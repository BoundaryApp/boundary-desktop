UX study · kanban task activity

See what the agents are doing, from anywhere in the app

When the Orchestrator files kanban tasks, Hermes runs each one as a separate worker process. Boundary watches only the turns it started itself, and the chat lists hide worker sessions. So the app goes silent while LM Studio shows the model hard at work. This study adds four layers, one for each question you have about delegated work. The live mock steps through them.

Recommendation: four layers, each answering one question
  1. Is anything working? A Working now section at the top of the chat rail, shown only while tasks run. Working dots on the assignee's DM row and on the Chat icon (that dot already exists; it gains worker runs).
  2. What is it, and where did it come from? Live task cards in the conversation that filed them. Each task page links back with "Filed in …".
  3. Is it making progress? A task page in the center pane. A liveness strip shows elapsed time, the heartbeat age and a now line (the newest console line). Below it sit the activity timeline, a collapsible console and the result. A composer posts comments that the running worker reads at its next step.
  4. Does it need me? A Needs you count on the Tasks row and in the list. An inline card on the task page for questions and reviews. An OS notification when the app is in the background.

Everything reads from Hermes's dashboard kanban plugin: /board, the /events WebSocket and /workers/active. Boundary already authenticates to the dashboard. No stack change is needed for Phases 1–3. See backend notes.

The moments

1 · Filed

Cards where you asked

The Orchestrator's kanban_create calls become live task cards. Working now appears in the rail at the same moment.

2 · Running

Alive, and doing what

Heartbeat age and the newest console line answer "is it stuck?" without reading logs. Notes steer the worker mid-run.

3 · Quiet

Slow is not dead

It turns amber after 3 minutes without a heartbeat and red only when the run crashes or its claim expires, so a long local-model call doesn't look like a failure.

4 · Needs you

One reply unblocks

A needs_input block shows as an interrupt card. Reply and resume comments and moves the task back to Ready.

5 · Done

The result, up top

The summary and the files written, with a link to the finished worker transcript.

Overview

Tasks, grouped by what to do

Needs you, Running, Up next and Done, filtered to the rail's project. Drag-and-drop stays in Hermes's board.

Directions considered

DirectionForAgainst
Link out to Hermes's boardNearly free: the dashboard already has a kanban tab.Answers none of the four questions inside Boundary. You still have to think to go and look.
A Board destination in the icon rail, with columnsA familiar kanban mental model.Columns answer "what's on the board", not "what's happening now". The view is wide and drag-heavy, which clashes with the centered chat workbench (ADR 0020). It also duplicates Hermes's board.
Show worker sessions as chatsReuses the transcript view.Workers aren't conversations. Hermes hides them on purpose. No live stream exists for them (they're subprocesses), and they'd flood the rail.
Layered: rail signal → cards → task page → listEach surface answers one question where you already are. It is quiet when nothing runs, and it builds only on existing dashboard APIs.More surfaces to build. It needs a WebSocket feed in main, a new pattern next to the gateway connection.

Open questions

  1. Done notifications: always, or only for tasks filed from a conversation you sent from in the last 24 h? The spec proposes the latter.
  2. Project filter: a task belongs to a project when its workspace_path sits inside the project's folder. Scratch tasks have no folder; they would show only under "All projects". Is that acceptable?
  3. CR 0005: ask the stack to put the current tool name in heartbeat events, so the now line comes from the push feed instead of polling the log tail?
