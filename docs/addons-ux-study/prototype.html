Pinned or independently updated?

Keep every add-on pinned. Move the pins out of the stack release cadence, though, so an add-on can get a tested update without waiting for a whole stack release.

Floating tags (latest, 1) are a poor fit here for three reasons that apply to services like Twenty in particular:

  • Twenty, Vikunja, n8n and similar apps run database migrations on start. A floating tag that pulls a new minor migrates the data one way, and the stack’s rollback (updates plan phase 6) can’t undo it. The stack already treats hermes, n8n and db data as one-way.
  • Each add-on also has an integration half that the stack owns: the MCP bridge, the bootstrap that registers it with Hermes, and the env it reads. An upstream API change breaks the agent’s tools even when the app itself starts fine.
  • Boundary’s contract checks (ADR 0031) and the stack’s own CI can only vouch for a version they ran.

What changes is where the pin lives. Today an image pin is a default in docker-compose.yml, so moving it means a stack release, and in Boundary a new compiled pin. With the signed channel file from updates plan phase 5, each add-on can carry its own entry: image digests, the stack range it works with, and whether the update migrates data. Boundary then offers an add-on update the same way it offers a stack update: back up that add-on’s data, pull while the old version runs, swap, health-check, and keep the previous digest for a rollback until the user confirms.

A reasonable policy for the UI:

Update kindBehaviour
Patch with no migration, testedInstalls on the next stack restart without asking, like a stack patch. Shown in Updates afterwards.
Migrates dataAsks first, backs up the add-on’s data, then installs. Rollback restores the backup.
Security fix flagged in the channel fileAsks with a stronger prompt and a date; never silent, because it may migrate.
Version the stack hasn’t testedNot offered. Developers can still set the *_IMAGE override in a local stack.

This needs stack requests R1, R7 and R8 below. Until they land, add-ons follow the stack pin, which is what the prototype’s detail screen says under Updates.

Change requests for the agent stack

Filed as docs/change-requests/0020-ui-installable-addons.md, where the stack’s replies sit under each item. In short: memory limits, healthchecks and secret files are planned for 0.3.10, along with Twenty. The manifest (with install, connect and backup fields), addon.sh and removal come in a later 0.3.x patch. Hermes’s reload.mcp answers R4 once the stack’s live check passes. The capabilities list and per-add-on pins wait, and a shared database for Twenty is declined. The asks as first written: Each builds on what the stack already has: one *_ENABLED flag per optional service, sync-profiles.sh, and make services.

#AskWhy Boundary needs itPriority
R1An add-on manifest per optional service (addons/<id>/addon.json, or one addons.json): id, name, one-line description, flag, profile, images with digests and architectures, memory reservation and limit, disk estimate, published ports, the services it depends on, config keys (type, required, secret, generator, validation), tools it gives Hermes, which services must restart, data paths and whether they migrate one way, the stack version that added it.Every screen in the prototype reads from this. Without it Boundary hard-codes a catalog per stack release, the same problem 0017 R2 describes for release metadata.Blocking
R2Memory reservations and limits on every optional service (deploy.resources). In stack v0.3.9 only hermes and hermes-webui set a memory limit; no optional service does.The fit check compares those numbers with the 12 GiB engine. Without limits the numbers are guesses and one add-on can starve Hermes.Blocking
R3A non-interactive enable and disable step per add-on, e.g. scripts/addon.sh enable twenty --json, that writes the flag, runs sync-profiles.sh, runs the add-on’s one-time setup (create its database in the shared Postgres, first workspace, an API key for its MCP bridge), and prints one JSON line per phase with progress.The install screen’s steps map to these phases. First-time setup belongs to the stack, since another client would need it too.Blocking
R4Register or remove an MCP server on a running Hermes without recreating it: a gateway method or an API route that re-reads mcp_servers from config. POST /v1/mcp/servers/{name}/reconnect exists today but only reconnects a server Hermes already knows.Removes the “Restart assistant” step for most add-ons. Restarting Hermes interrupts turns and kanban runs.Wanted
R5Installed add-ons with their versions in gateway.capabilities (extends 0017 R3), and a health check on the long-running services that lack one (n8n).Boundary shows On, Starting or Failing per add-on without parsing container names.Wanted
R6Defined removal: disabling keeps data; a separate remove --delete-data drops the add-on’s database and folders; both remove its MCP registration.The prototype offers Turn off and Remove and delete data as two actions. Today a flag at 0 stops the profile and leaves data in an undocumented state.Wanted
R7An image override and a compatible stack range per add-on in the manifest, and a CI smoke test per add-on (start, health, one MCP tool call).Lets the signed channel file move an add-on’s pin between stack releases.Later
R8Secret config through key files, as llm-proxy already supports with *_FILE keys, rather than .env.Generated secrets and API keys stay out of .env and docker inspect; Boundary keeps them in its own store.Wanted
R9Run add-on databases in the shared Postgres (db profile) where the app supports it, and share one Redis/Valkey.Twenty alone otherwise brings its own Postgres and Redis, roughly doubling its memory.Later

Boundary fallback until R1 to R3 land: a catalog in Boundary for the add-ons of the pinned stack, an enable path that sets the flag in Boundary’s compose env (as it does for GPTR_MCP_ENABLED) and recreates Hermes, and the fit check run against docker stats after start rather than before.

Figures in the prototype

Engine size (12 GiB) and disk (100 GiB) are Boundary’s Podman machine defaults. Twenty’s version, containers, port, idle memory, image size and owner account come from the stack’s reply to 0020. Tasks’ tool counts come from the stack’s Tasks docs. The Local models and Signal figures are placeholders until the stack’s manifest reports them.
