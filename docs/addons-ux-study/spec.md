## Goal

A user sees the optional services their stack offers, learns before installing whether this Mac can run one and what it costs, and installs or removes it from Boundary with progress for each step. Nothing asks them to run a `make` target or edit `.env`.

## Decisions

1. **Add-ons live under Services.** They are services the assistant runs, beside the existing service cards. What an add-on's agents may do is set on its own page (decision 7).
2. **The catalog comes from the stack.** Boundary reads `addon.sh list --json` once the stack ships it (0020 R1). Until then Boundary compiles a catalog for the pinned stack in the same shape, so phase 4 swaps the source without touching the page.
3. **Only services Boundary doesn't already start are add-ons.** Boundary always runs `core`, `automation`, `coding`, `db` and `research`, so those aren't listed. n8n and LightRAG ship in the stack as built-in add-ons (change request 0020 R10, stack 0.3.13) and are listed like the others: off until the user gets them, then turned on and off through `addon.sh`. `automation` stays on for `gptr-mcp`, so `up` leaves n8n's services out while n8n is off. Messages is left out: it reads the user's real messages and needs a consent flow of its own, which this spec doesn't cover. Email joins in phase 9 with its own consent step (decision 33). Twenty is the first add-on built end to end and joins the catalog with stack 0.3.10. Actual Budget joins in phase 7 and Bitwarden in phase 8. Tasks, Local models and Signal follow once `addon.sh` exists.
4. **The fit check is drawn against the container engine.** Add-ons compete for the Podman machine's memory (half the Mac's memory, between 4 and 12 GiB), not the Mac's. The check uses each add-on's reservation from compose (0020 R2), and `docker stats` for running services that have no limit yet, including core's `hermes-worker`, `llm-proxy`, `searxng` and `mcp-searxng`. When an add-on doesn't fit, the page offers to grow the engine and says that this restarts the stack.
5. **One Install button per add-on.** It turns on the manifest's `install` flag set. Twenty's turns on both `TWENTY_LOCAL_ENABLED` and `TWENTY_MCP_ENABLED`. Connecting a hosted Twenty is a separate action on the same page, offered beside Install before either is set up. It runs `crm.sh add` with the keys in its environment, starts no containers, and turns on `TWENTY_MCP_ENABLED` alone. `TWENTY_MCP_ENABLED` is 1 while the local instance is installed or a hosted workspace's file is active (not parked). While the local instance isn't installed, its own workspace file stays parked, so it doesn't count.
6. **The user chooses only what the stack can't.** Secrets and accounts are generated at install. The one choice offered before install is what agents may do, where an add-on supports it.
7. **What agents may do has two settings for now.** **Look things up** maps to the add-on's read-only key and **Make changes** to the write key. For Twenty, `TWENTY_ACCESS=read|write` in each workspace file picks the key, and each workspace has its own setting. A third, **Make changes after asking you**, joins when the stack can ask before writes only (decision 8). Unattended runs get the read-only key whatever the setting. The read-only key is described as the stack's docs describe it: if Twenty's read-only role can still write junction records, the page says what it can still write instead of calling it read-only.
8. **Approval waits for the stack.** Twenty routes every record call through `execute_tool`. Hermes v0.22.7 asks before an MCP call only by tool name, on a `trust: untrusted` server, for tools without `readOnlyHint=true`, so it would ask before every lookup too. Policy stays in the agent (ADR 0006): 0023 R3 asks the stack to ask before writes only, and Boundary answers those prompts with its existing approval card.
9. **Install is a list of steps with one progress bar.** Steps come from the stack's JSON lines once `addon.sh` exists (pull with bytes where compose reports them, setup steps as `running` then `done` or `error`). A failure shows the step's `logTail` and offers **Try again** and **Undo install**. The user can leave the screen; the Services icon shows a dot until it finishes.
10. **The restart step is the last step and waits for the user.** Until the stack's `reload.mcp` path ships, installs end by recreating Hermes, with **Restart when the task finishes** offered while agent work runs. After it ships, the step becomes a reload that needs no restart, and the page still says that each chat on the profile re-sends its history uncached on its next turn.
11. **Twenty opens signed in, and its owner login stays out of the agents' vault.** The install asks for no email or password, and a profile step names the owner after the Mac account's full name and finishes Twenty's welcome steps (0023 R5). **Open Twenty** asks for a fresh one-time login link each time (0023 R4) and opens it, so the browser lands in the CRM signed in. Passwords & Logins holds logins agents use, and the owner is a server admin, so storing it there would bypass the roles behind decision 7. The local row offers **Copy password** for another browser or device; the main process reads it from the stack's settings and the renderer never receives it.
12. **Turn off keeps data; removal is separate and runs as steps.** **Turn off** runs `disable`. While a hosted workspace is connected it stops only the local instance, and agents keep the hosted workspace. **Remove and delete data** asks the user to type a confirmation, offers to delete the downloaded images too, then closes and shows the install's progress view: stop, remove containers, delete data, remove the owner sign-in and keys, delete images if chosen, and restart the assistant when Twenty was on. The user can leave the screen. A failure shows the step's log and **Try again**, with no undo. Hosted workspaces stay.
13. **Add-ons stay pinned.** An add-on updates with the stack until the signed channel file can carry its own tested pin (0020 R7). Updates that migrate data ask first and back up the add-on, using the manifest's `backup` object; Twenty's needs its profile stopped for the copy.
14. **A local stack keeps what Boundary installed.** Against a developer's own checkout, Boundary acts on the stack rather than holding the add-on's state for itself: an install has the stack's `addon.sh` write the add-on's flags to the checkout's `.env` and sync `COMPOSE_PROFILES`, and Turn off sets them back to 0, so the stack's own `make up` starts the same services with or without Boundary open.
15. **An installed add-on that isn't running gets asked about.** When the stack is ready and an installed add-on's server isn't running, a card on every screen and the add-on's page offer **Start** or **Mark as not installed**. Start brings up its containers, waits for its server to report healthy and restarts the assistant so agents reconnect to its tools. Mark as not installed is Turn off: data stays. **Later** hides the card until the next launch; the Services icon keeps its dot.
16. **One workspace per row, and one bar for changes that wait for a restart.** Twenty's page lists the local workspace and each hosted one under the name agents use (`crm-main`, `crm-<name>`). Connect, disconnect, an access change and Turn off each add a line to one bar with **Restart assistant** and **Later** (or **Restart when the task finishes** while agent work runs), until the stack can reload tools without a restart.
17. **Moving from this Mac's Twenty to a hosted one is guided, not automatic.** With both connected, the page shows three steps: connected, copy your records with Twenty's own export and import, and turn off or remove this Mac's Twenty. **Keep both** hides them.
18. **Actual Budget is a list of connected budgets.** Actual's page lists each budget under the name agents use (`budget-<slug>`), with its server, its access and whether its sign-in still works, as Twenty's page lists workspaces (decision 16). Each row is one `addon.sh connect actual` (0026 R1), which the stack registers through its generic `mcp.instances` path as one `budget-<slug>` entry on each profile in the row's `bind`: the owner's profile, `default`, `browser`, and `api-server` read-only. Connecting a budget to another person's profile waits for guest agents and shared services. From stack 0.3.14 the stack no longer reads the v0.3.12 single budget (`ACTUAL_BUDGET_FILE`), so the page has no row for it.
19. **Two ways in: this Mac's server, or one the user already runs.** **Get** installs Actual on this Mac: it turns on `ACTUAL_LOCAL_ENABLED` and `ACTUAL_MCP_ENABLED`, starts the `budget-local` and `budget` profiles, has the stack generate the server password and create a first budget, and connects that budget as the first row. The user types nothing. **Connect a budget** sits beside **Get** and stays on the page afterwards. It asks for a server address and password, starts only the MCP containers (`ACTUAL_MCP_ENABLED`), and adds a row. While Actual is off, the first such budget runs as an install: **Connect** closes the sheet and the page shows the install's steps (check, download, start, connect), because the first `enable` builds the MCP images and takes minutes. With only such budgets, Actual is on in the store and the Installed list, since their MCP containers run on this Mac, and has no **Open**.
20. **Boundary asks for a password and keeps neither it nor the token.** The connect sheet asks for the server address and password, then lists the budgets on that server to pick from. The name agents use comes from the budget's name, lowercased with dashes, and the user can change it before connecting. When the chosen budget is end-to-end encrypted, or after an `encryption_password` error, it adds a field for the encryption password. `connect` exchanges the password for a session token and stores only the token, in the stack. The password goes from the sheet to the main process to `budget.sh`'s environment, and nothing in Boundary keeps it. A server with password sign-in off (OpenID) gets **Use a session token instead**, which explains copying the token from Actual's web app. This replaces 0026's answer 2, where Boundary kept the credential.
21. **Look things up is preselected, for each budget.** The access choice (decision 7) defaults to **Look things up** on every budget, because a budget is financial data. With it, `connect` gets no `bind`, which the stack reads as read-only on every profile, so chats get `budget-<slug>` with its 18 read tools. **Make changes** sends `bind` `{"default": "rw", "browser": "rw", "api-server": "ro"}`, and the same entry also gets the 32 write tools. A row's access changes through `budget.sh access`, which rewrites the `bind`, without reconnecting. The row shows write access when `bind.default` is `rw`. Unattended runs and `api-server` get only the read tools whatever the setting.
22. **A sign-in that stopped working shows on the row.** Hermes passes tool errors to the model, not to Boundary, so Boundary runs `budget.sh status --json` when the stack becomes ready and when Actual's page opens. It doesn't poll. A row in any state other than `ok` shows that state's message from the table in phase 7. `token_expired`, `login_refused` and `encryption_password` also offer **Sign in again**, which reopens the sheet with the row's name, server and access filled in and replaces the connection. The stack's `connect` has no `--force`, so Boundary disconnects the row first and the sheet says so (0026 round 7). The Installed list and the dot on the Services rail icon show it too.
23. **Open Actual.** This Mac's rows offer **Open Actual** (`http://localhost:<ACTUAL_PORT>`, 5006 by default) and **Copy password**, which the main process reads from the stack's settings so the renderer never receives it. Actual has no sign-in link, so its web app asks for the password. A remote row opens its server address.
24. **Turn off and removal follow decision 12.** **Turn off** stops this Mac's server and sets `ACTUAL_LOCAL_ENABLED` to 0, through `addon.sh configure` and `enable` while a remote budget is connected and `addon.sh disable` otherwise. Remote budgets stay connected. This Mac's rows stay listed, marked as off, and work again after **Turn on**. While a remote budget keeps the add-on on, the stack keeps this Mac's budgets registered with the server off, so agents still list their tools and the calls fail; the confirmation says so. With no remote budget, `addon.sh disable` turns the add-on off and agents lose every budget's tools. **Disconnect** on a row runs `budget.sh disconnect`, which removes the entries, the stored token and the MCP cache, and leaves the budget on its server. **Remove and delete data** disconnects this Mac's rows, then deletes the server's data folder (`ACTUAL_DATA_DIR`) and, if chosen, the images. The confirmation says that this Mac's budgets have no other copy and asks the user to type it.
25. **Connecting reloads the tools in place.** From stack 0.3.13, `addon.sh connect` and `disconnect` and `budget.sh access` run the Hermes bootstraps and ask the gateway to reload, without recreating Hermes or needing `make`. The sheet and the access switch say that chats started afterwards get the change, and nothing goes in the restart bar, as for Bitwarden (decision 32).
26. **Bitwarden connects accounts the person already has.** Bitwarden joins in phase 8 for bitwarden.com accounts (US or EU) and the person's own Bitwarden or Vaultwarden over HTTPS. The stack's local Vaultwarden mode waits for a later phase, because its setup includes waiting while the person registers in the web vault. **Get** turns on `BITWARDEN_ENABLED` and opens the connect sheet, since the add-on does nothing without an account. The page says the logins work in chats on the owner's profile and in the browser, never in scheduled jobs or the API profile, because the stack's `credentials` read class keeps them off `api-server` and out of cron.
27. **One account per row.** Bitwarden's page lists each account by its name, with its server, its folder, how it unlocks and its state, all from `vault.sh status --json` (0028 R2), not from `addon.sh list`, which misses accounts added at the terminal. The states are unlocked, locked, offline, not working and refused. The broker checks a manual account's API key when the account connects and at its first sign-in only, so a key revoked later doesn't show on the row; what an unlock or sync reports then is still open. While the broker is down every row is offline with one note saying so (`broker_down`). An account connected while the broker was running but not yet loaded by it is offline with `not_loaded`, and says it starts with the next restart. An account file the stack can't read is refused (`bad_file`) and shows as a row naming the file. From stack 0.3.14 a refused row can also be `bad_slug` or `missing_client_id`, and the second offers **Connect again** (the refused-row table in phase 8). The `local` account and a terminal-added `scope: all` account show without controls to change them. An account added at the terminal before 0028's release has no **Disconnect** until the next `make up` records it, and one whose name breaks the rule in decision 28 never has one; the row says to remove it at the terminal. The page reads the state when the stack becomes ready, when the page opens, and after every connect, disconnect, unlock and lock. It doesn't poll.
28. **The connect sheet asks for the API key and a folder, and Boundary keeps neither.** It asks for the server (**bitwarden.com (US)**, **bitwarden.com (EU)** or a self-hosted HTTPS address), the account's personal API key (`client_id` and `client_secret`, with a link to where Bitwarden shows it under **Settings → Security → Keys**) and a folder, **Agent** by default. The account's name starts with a letter, uses lowercase letters, numbers and dashes, has at most 31 characters and isn't `local`; the sheet checks this before it sends anything. The sheet tells the person to create that folder and move the logins the agent may use into it from any Bitwarden app; Boundary never asks for their email and master password to do it. **Advanced** takes an organization collection ID instead, for an organization that grants a separate member account one collection. The main process sends the values to `addon.sh connect bitwarden` on stdin (0028 R1), and the renderer passes them through without storing them.
29. **Ask me each time is the default unlock.** **Ask me each time** (`manual`) stores no master password, and the person unlocks after each stack restart. **Keep me unlocked** (`stored`) asks for the master password at connect, and says before it's chosen that the stack then holds a password that opens the whole vault, while the agent sees only the folder. A locked account shows **Unlock** on its row and a dot on the Services icon. After a restart, one card lists the accounts to unlock. **Unlock** opens a masked field whose value goes to `vault.sh unlock` on stdin (0028 R3). **Lock** is on each manual row. A wrong master password leaves the account locked with a message, and Boundary allows one try per press, as the stack does. Connecting or disconnecting an account restarts the broker, which locks every other manual account, so the sheet says so first when any are unlocked, and the unlock card appears afterwards.
30. **Access requests are approved in Bitwarden.** When the agent asks for a login it can't reach, the page lists the request with its site, its account and the agent's reason, shown as the agent's words. It says to move the login for that site into the folder in any Bitwarden app, and **Check now** runs `vault.sh sync --json` (0028 R4), after which the request clears. While another sync is running it says to try again in a moment, and within 30 seconds of the last sync it shows that sync's result. Boundary reads `vault.sh requests --json` when the stack becomes ready, when the page opens, and after a chat turn that called `bitwarden_request_access`. The Services icon shows a dot while any request is pending. Boundary never says whether a matching login exists. A grant dialog in Boundary would need the person's own master password, so it waits for a later phase.
31. **A returned login stays in the folder until the person moves it.** When the agent hands a login back, the broker stops listing and filling it at once, but it doesn't move it. The person moves it out of the folder or collection in any Bitwarden app, and the next sync that no longer finds it in scope clears it. Nothing in the stack tracks returned logins, so the page doesn't list them; the agent's tool result tells the agent. 0028 R6 asked for that list and was withdrawn before release.
32. **Turning Bitwarden on or off doesn't restart the assistant.** From stack 0.3.13, `enable` and `disable` run the bootstraps and ask the gateway to reload its plugins, without recreating Hermes. Chats that are already open keep the tools they started with, so the page says new chats can use the logins, and no line goes in the restart bar. **Disconnect** on a row runs `addon.sh disconnect bitwarden`, which deletes the account's file, secrets and `bw` data, and reminds the person to revoke the API key in Bitwarden. Disconnecting an account whose file is already gone ends with `done`, so pressing **Disconnect** again after a failed broker restart clears the row. **Turn off** keeps accounts (decision 12). **Remove and delete data** deletes them all. Nothing in Bitwarden itself changes.
33. **Email asks for consent before the first account.** Email is the stack's `email` add-on (`addons/email/addon.json`), which indexes IMAP accounts read-only and serves the index to Hermes. **Get** installs nothing: the stack's `enable` refuses without an account that has mailboxes, so Get opens the connect sheet, as Bitwarden's does. Before the first account the sheet's first step says that agents in chats on the owner's profile can search and read the mail the person chooses, from an index on this Mac, and that scheduled jobs and the API profile never get it; that agents can't send, and drafts are a separate switch that is off; that anyone who emails the person can put instructions in a message, which the agent reads as text; and that the password is kept in the stack's files on this Mac, readable only by the container that logs in, and Boundary doesn't keep it. Its button is **Choose an account**. The `email-local` add-on, which reads through Mail.app, isn't offered.
34. **Accounts start from a provider.** The sheet offers **iCloud**, **Gmail**, **Fastmail**, **Yahoo** and **Other**. A known provider fills in the server, port 993 and TLS, and asks for the email address and an app password, since all four refuse the account password over IMAP. iCloud reuses the calendar's app-password walkthrough; the others show their steps and a link to the provider's page. **Other** asks for the server, port, security (TLS or STARTTLS), user name, From address and password. **Plain** appears only for `localhost`, `127.0.0.1` and `host.docker.internal`, the hosts the stack accepts it for, which covers Proton Bridge; the sheet marks Proton as untested. Outlook.com isn't listed, because it no longer accepts a password over IMAP. The name agents use, the account id in search results, defaults to the provider's (`icloud`, `gmail`, `fastmail`, `yahoo`, `mail` for Other) and follows the stack's rule: a lowercase letter, then up to 30 lowercase letters, digits and dashes.
35. **The sheet checks the login by listing mailboxes.** **Next** stores the account through `addon.sh configure email --instance <slug>`, with every value and the password as JSON on stdin, then runs `addon.sh run email mailboxes --instance <slug>`, which logs in and lists the mailboxes with their message counts. The first listing builds the email image, so the step says it takes a few minutes the first time. A refused login keeps the sheet on the account step with the stack's message. **Cancel** on an account that has no mailboxes yet removes it (`configure --instance <slug> --remove`), so a wrong password isn't left stored.
36. **Mailboxes and a window, then Connect.** The mailbox step lists every selectable mailbox with its count. Inbox and the mailbox flagged `\Sent` start checked; Junk, Trash, All Mail and Flagged are listed unchecked. **How far back** offers **Last 90 days** (the default), **Last 30 days**, **Last year**, **Everything** and a date. **Everything** stores `1970-01-01` and says the first pass can take hours on a large mailbox. Message bodies are always indexed (`bodies: true`); **Include attachment text** is off. The window and attachment text apply to every account, so for a later account the step shows them as set and says where to change them. Connecting the first account closes the sheet and runs as an install (check, start, first pass). A later account restarts `email-indexer`, so its first pass starts at once rather than after the interval (15 minutes).
37. **One account per row, with the last pass's result.** Email's page lists each account from `addon.sh list --json` with its name, address, server and mailboxes. Its state comes from the indexer's log: each pass prints one JSON line with totals and `failed`, a map from account id to 4 (login refused or password missing) or 5 (server error or unreachable), and an account the indexer leaves out prints `email-indexer: <slug>: <reason>`. A row shows **Waiting for the first pass** until a pass ends after the account's last change, **Indexed** with the pass's time, **The server didn't accept the password** with **Change password**, **Couldn't reach `<host>`**, or **Left out** with the reason. Under the list the page shows the index's total and the last pass's time; counts per account wait for 0031. The page reads this when the stack becomes ready, when it opens and after every change, and while it is open and a pass is owed it reads again every 30 seconds until the pass line arrives. A refused login puts a dot on the Services icon. **Mailboxes** on a row reopens the mailbox step, **Change password** reopens the account step with everything but the password filled in, and **Remove** deletes the account and its password and restarts the indexer, so its messages leave the index on that pass.
38. **Drafts, Turn off and removal.** The settings card has **How far back**, **Include attachment text** and **Let agents save drafts (never sends)**. Drafts runs `configure email` with `drafts`, then `enable`, because a gate flag changes only at the next `enable`; the stack then saves each draft to the account's Drafts mailbox over IMAP. A change to the window or attachment text restarts the indexer. **Turn off** runs `disable email` and keeps accounts, passwords and the index. **Remove and delete data** asks the person to type a confirmation, then runs `disable` and `remove email --delete-data`, which delete the index, the drafts queue and the stored passwords, and says nothing changes on the mail servers. `enable` and `disable` reload Hermes without a restart (decision 32), so the page says new chats get the change and nothing goes in the restart bar.

## Open work outside the UI

Confirm each against source when its phase starts, as the stack contract requires.

- **First-time setup without host tools.** `crm.sh init` and `todo.sh init` need `python3` 3.9 or later on the host, and the Makefile wraps them; a Mac without the Command Line Tools has neither. 0020 R11 asks the stack to run setup in a container. Boundary develops against `crm.sh init` meanwhile, and release builds wait for R11.
- **Release gating.** Builds pinned to a stack without the `crm` profile must show no Twenty entry. The catalog shows an add-on only when the installed stack tree has what it needs.
- **Approval before writes.** Waits on 0023 R3 (decision 8).
- **Twenty v2.55.0 behaviour.** The `/verify?loginToken=` route, `LOGIN_TOKEN_EXPIRES_IN`, the welcome steps a new owner sees, and what export and import can move were read from Twenty's `main` branch. Confirm each in the pinned image before phase 4 relies on it.
- **A changed owner password.** **Open Twenty** and **Copy password** read the password from the stack's settings. If the user changes it in Twenty, both break until `TWENTY_PASSWORD` (or the file `TWENTY_PASSWORD_FILE` names) is updated. Phase 5 needs a way to update it.
- **Actual's stack side (0026 R1, R2, R4, R5).** `budget.sh connect`, `disconnect`, `access`, `status`, `budgets` and `init --server-only`, and `addon.sh connect`, are on the stack's `main` and ship in 0.3.13. Phase 7 is built against that checkout; release builds wait for the tag and a pin bump.
- **Replacing a budget, the first budget, and Turn off (0026 round 7).** `connect` has no `--force`, so **Sign in again** and replacing a name disconnect first. The init hook's `sync_id` and `name` don't reach `enable`'s `done` line, so Get lists the local server's budgets after `enable`. Turn off can't park this Mac's rows, so while a remote budget keeps the add-on on, agents keep tools that fail until **Turn on**. The stack accepted the first two and hasn't built them: `connect --force` that swaps only after its checks pass, and `sync_id` and `name` in `enable`'s `done.result`. It decided against parking: from 0.3.14 a budget on the local server stays registered while `ACTUAL_LOCAL_ENABLED` is off (decision 24). Turning the local server back on is then `configure actual {"local": true}` and `enable actual --reinit` when the add-on was first enabled with it off. Boundary moves to each once a release has it.
- **Reload without a recreate or `make` (0020).** Shipped for Actual in 0.3.13: `addon.sh` and `budget.sh access` run the bootstraps and `vault.sh reload-plugins` with `docker compose` directly (decision 25).
- **Actual's memory figures and image.** No Actual service has a memory reservation or limit in compose on the stack's `main`, so the catalog's 0.6 GiB reservation and 0.6 GB download are estimates (the server, both MCP containers and one budget at about 200 MB, from 0026's measurement). `actual-mcp` is built from the stack's tree (`${IMAGE_PREFIX}-actual-mcp:local`) by `enable`'s `up`, not pulled. Measure both on the first live install.
- **Removing this Mac's budgets.** `addon.sh remove actual --delete-data` deletes `ACTUAL_DATA_DIR` and the whole add-on store, remote budgets' tokens included. Boundary uses it only when no remote budget is connected; otherwise it disconnects this Mac's rows and deletes `ACTUAL_DATA_DIR` and the server password itself.
- **Bitwarden accounts without a terminal (0028).** R1 to R5 and the broker change that signs manual accounts in at start are on the stack's `main` (merge a26f93c); R6 was withdrawn, tested against a stub `bw` only and not yet released. Phase 8 is built against that checkout; release builds wait for a tag and a pin bump. R2 to R4 are direct `vault.sh` calls, not `addon.sh` commands, because those run in a new container that can't reach the broker.
- **Removing Bitwarden's data.** `addon.sh remove bitwarden --delete-data` deletes `data/addons/bitwarden` but not the account files under `compose/bitwarden/accounts/`. Boundary disconnects each account with a store entry first; accounts added at the terminal without one stay, and the removal says so.
- **A revoked API key.** The broker doesn't catch a key revoked after connect (decision 27), and nobody has seen what `unlock` or `sync --json` reports for one. Revoke a test account's key when phase 8 starts, and map what comes back.
- **Two-step login.** Bitwarden's CLI docs say a personal API key sign-in skips two-step login, so the stack adds no error for it. Nobody has tried it on a real account with two-step login on. Try one when phase 8 starts.
- **Email's status and listing errors (0031).** The indexer's pass line has totals only, and `addon.sh run` exits 4 for every listing failure, so Boundary reads per-account state from the log and shows the listing's last `mail-index:` line. 0031 asks for `run email status` with counts, the last pass's time and failures per account, and for named listing errors. Boundary moves to each once a release has it.
- **Email's memory figures and images.** No email service has a memory reservation or limit in compose at v0.3.13, and all three images (`email-imap`, `mail-mcp`, `mail-drafts-mcp`) are built from the stack's tree. The catalog's figures are estimates; measure them on the first live install.
- **Contract table.** Each phase that reads something new from the stack adds it to `docs/stack-contract.md` with its check.

## Phases

**1 Prototype matches the stack's replies.** Twenty's four containers, port, size and generated values; no **Set up** form; the access choice; the hosted connect flow; the owner account handed to Passwords & Logins; a catalog of services Boundary doesn't already run.

**2 Add-ons page and fit check.** The page under Services with the compiled catalog, the engine memory bar, and the detail page with the fit check and what it runs. Installs nothing. The fit check is a pure function with unit tests for room to spare, tight and won't fit.

**3 Install and remove Twenty.** `TWENTY_LOCAL_ENABLED` and `TWENTY_MCP_ENABLED` in Boundary's compose env, `setup.sh --crm`, the `crm` profile started, `crm.sh init`, Hermes recreated at the restart step, **Turn off** and **Remove and delete data**. Developed against the stack's Twenty work through `BOUNDARY_ASSISTANT_ROOT`. A mounted test runs the install screen against a fake stack that fails at setup and checks **Undo install**. A `test:stack` case covers a `crm-main` server on the default profile.

**4 Twenty workspaces, access, sign-in and removal steps.** **Connect a hosted workspace** through `crm.sh add` and **Disconnect** through `crm.sh remove`; the workspace list and the restart bar; the two-setting access choice per workspace; Turn off that keeps hosted workspaces; the guided move to a hosted workspace; **Open Twenty** signed in and **Copy password**; the profile step; removal as steps. Each stack dependency in 0023 has a Boundary fallback except R5, so phase 4 ships on stack 0.3.10.

**5 Install through `addon.sh`, then Tasks and the rest.** The catalog from `addon.sh list --json`, steps from `enable --json`, removal through `disable` and `remove`, and the reload in place of the recreate once the stack's release notes say so. Boundary's compiled catalog and its Twenty glue go away, and Tasks, Local models and Signal join.

**6 Add-on backups and updates.** Backups from the manifest's `backup` object, with Twenty stopped for the copy, and add-on updates from the signed channel file.

**7 Actual Budget: this Mac's server and connected budgets.** Actual in the store with **Get** and **Connect a budget** (decision 19); the local install with its first budget connected; the connect sheet with the budget picker, the encryption password field and the session token link; budget rows with access, **Sign in again**, **Disconnect**, **Open Actual** and **Copy password**; `budget.sh status` when the stack becomes ready and when the page opens; Turn off and removal as steps. ## Acceptance criteria

- [x] The Add-ons page lists no service Boundary already starts.
- [ ] The fit check says whether an add-on fits before anything downloads, and offers the engine resize when it doesn't.
- [ ] A user installs Twenty without typing anything, and its tools answer in the next chat.
- [ ] A failed install leaves the stack as it was after **Undo install**.
- [ ] **Turn off** then install again keeps the add-on's data.
- [ ] In a local stack, `make down` then `make up` after an install starts the add-on again, and after Turn off it doesn't.
- [ ] An installed add-on that isn't running when the stack is ready shows the card; **Start** brings its tools back and **Mark as not installed** records it off.
- [ ] No install step prints or stores a generated password outside the stack's own files, and the renderer never receives one.
- [ ] A hosted Twenty workspace connects without starting a container, and its tools answer in the next chat after the restart.
- [ ] Turning off this Mac's Twenty with a hosted workspace connected removes `crm-main` from agents and keeps the hosted one.
- [ ] Removing an add-on shows its steps, keeps going when the user leaves the screen, and says what's left after a failure.
- [ ] **Open Twenty** opens this Mac's workspace signed in, with no sign-in page.
- [ ] With **Make changes after asking you** (after 0023 R3), a Twenty lookup runs without a prompt and a record change waits for approval.
- [ ] Installing Actual on this Mac connects its first budget without the user typing anything, and a lookup works in the next chat.
- [ ] Connecting a budget on another server asks only for its address, its password and which budget, and Boundary keeps neither the password nor the session token.
- [ ] A budget connected with **Look things up** gives chats no tool that changes it.
- [ ] A budget whose sign-in stopped working shows **Sign in again** on its row before anyone asks about it in chat.
- [ ] **Remove and delete data** deletes this Mac's Actual data after a typed confirmation, and budgets on other servers stay connected.
- [ ] Connecting a bitwarden.com account asks for its API key, a folder and how it unlocks, and Boundary keeps none of the values.
- [ ] With **Ask me each time**, the account shows **Unlock** after a stack restart, a wrong master password leaves it locked with a message, and the right one unlocks it.
- [ ] A login the agent asks for appears as a request on Bitwarden's page, and clears after the person moves it into the folder and presses **Check now**.
- [ ] Turning Bitwarden on gives a new chat the Bitwarden logins without restarting the assistant.
- [ ] **Disconnect** removes the account and its stored secrets from the stack, and says to revoke the API key in Bitwarden.
- [ ] Before the first email account, the sheet says what agents can read, that they can't send, that mail can carry instructions, and where the password is kept.
- [ ] Adding an iCloud account asks only for the address, an app password, the mailboxes and how far back, and Boundary keeps no password.
- [ ] A refused app password keeps the sheet on the account step with a message, and **Cancel** leaves no account stored.
- [ ] After Connect, a new chat on the owner's profile finds a message from the chosen mailboxes and window, and the API profile and scheduled jobs have no email tools.
- [ ] An account whose password stopped working shows **Change password** on its row after the next pass.
- [ ] **Remove and delete data** deletes the index and stored passwords after a typed confirmation, and nothing changes on the mail server.
