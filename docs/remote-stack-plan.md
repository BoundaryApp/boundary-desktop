## Phase 1: the interface, local only

No behaviour changes. Each step lands on its own and keeps `bun run check` green.

**1a. The interface and the local host.** `src/main/services/stackHost/` holds the `StackHost` type (commands, files, endpoints, capabilities, per ADR 0062 §1), `LocalStackHost`, and `getStackHost()`. The local host wraps what exists: `getContainerRuntime` with `runCli`, `runCompose` and `runComposeStreaming` for commands; `tryResolveAssistantRoot`, `resolveAssistantDataRoot` and `resolveAssistantUserContentRoot` for locations; `getStoredAssistantPorts` for endpoints. `getAssistantStackAccess()` (`compose`, `composeWithInput`, `composeStreaming`, `scriptEnv`, `root`, `dataRoot`) becomes a thin layer over the host, since add-ons, calendars and Hermes config already use it. Until callers move in 1b–1d, `getStackHost()` stays private to `AssistantStackService`, and a fake host for tests arrives with the first caller that needs one.

**1b. Endpoints.** Every URL to the stack comes from the host's endpoints. Call sites that build `127.0.0.1` URLs today move over: the health and status URLs and `tryAttachToLiveLocalStack` in `AssistantStackService`, `waitUntilCodingAgentUp`, `codingAgentBusy`, `llmProxyAdmin`, `detectorClient`, `twentySignIn`, `twentyMemberKeys`, `actualAddon` and `circles/sharedServices`. Ports read from `.env` (`DETECTOR_PORT`, `TWENTY_PORT`) become named endpoints. `src/shared/assistantUiServices.ts` takes its base URLs from main over IPC instead of building them. The window's CSP is left alone, since forwarded ports are still on localhost. Code that only needs URLs gets them from `getStackEndpoints()`, which works before the stack is installed. A port the stack publishes outside the stored set (an add-on's port from `.env`, a port set being tried) goes through `portUrl`. Vikunja's add-on listing reports a web URL that Boundary accepts only on loopback (`vikunjaAddon.ts`); phase 4 maps it to the forwarded port.

**1c. Files.** `stackEnv`, `hermesProvision`'s profile helpers, `hermesAgents`' registry, `hermesConfigApply`'s read, and the overlay writers move onto the host's file operations, then the call sites that use `fs` on stack paths directly. Files only Boundary's local install uses (provisioning, `projectTreeSwap`, `stackDataBackup`, the `.boundary-bin` shims) stay as they are and sit behind the `provision` capability in phase 2.

Code that holds the folder it is setting up takes `stackFilesAt(root)`; everything else takes `getStackFiles()`. Writes are atomic, and a new file can be given a mode (profile `.env` files stay `0600`). Besides reading, writing, listing and removing, `StackFiles` has `stat` (kind and size, through links), `realpath` (relative to the location, null outside it), `rename` within a location, `writeBytes` and `mkdir` with a mode, each of which SFTP provides. The add-on flag and availability readers, the compose profile and env chain built on them, `twentyPort` and the Twenty workspace store (`twentyWorkspaces`, which Circles' shared services reach through an async `WorkspaceStore`) go through `StackFiles`. These still use `fs` after phase 1, and the 1e guard lists each of them:

- Files in project folders on this machine: `htmlPreviewFiles`, `writingCheckFiles`, `hermesReplyFiles`, `libraryProjectsRoot` in `hermesProjectSources`, and `projectSourcesModel`, whose sources are `~/` paths, absolute paths or paths under the project folder. They go behind `hostFolders` in phase 2. The source catalog also compares nanosecond modification times, which SFTP doesn't report.
- Writing voices read the sample files a person picks on this machine (`writingVoiceSamples`) and reveal a voice's folder in Finder (`writingVoicesIpc`). Everything else in `writingVoices/` uses `StackFiles`; deleting a voice still moves its folder to this machine's Trash, which phase 4 has to replace on a remote host.
- Paths `.env` may set to anywhere on this machine: `ACTUAL_DATA_DIR` (deleted with `fs` in `actualRuntime`), `TWENTY_PASSWORD_FILE` and `VIKUNJA_FILES_DIR` when they point outside the stack folder, and `BITWARDEN_HOST_DATA_DIR`, where `bitwardenFolders` creates the broker's folders until CR 0035 R1 ships.
- Folders on this machine bound into containers, and Boundary's own files beside the stack under Electron's userData: the coding folders and grants, context roots, `hermesProjects` (`createHostFolderHermesProject`, `createEmptyHermesProject`), the projects overlay (`writeHermesProjectsOverlay`) and the coding shadow file (`ensureCodingShadowSource`). They go behind `hostFolders` in phase 2. Revealing an agent's `SOUL.md` in Finder (`hermesAgents`) needs a path on this machine too.
- Local setup and location resolution: `assistantPaths` (`resolveAssistantUserContentRoot` reads `ASSISTANT_DATA_ROOT` through `readEnvFile`; the `ensure*` helpers), `resolveAssistantRoot`, `regenerateN8nCredentialsFromEnv` and `liveLocalStackFileArgs`.
- `src/main/migrations/assistantStack.ts` (`repairApiServerListenPort`) stays on `fs`: it repairs the managed install's own profile, the startup migration runner is synchronous, and the migration is due for deletion after 0.1.0.

**1d. Commands.** `runSovereignSetup`, the add-on flag writer's `sync-profiles.sh` (removed in 3a) and `runScriptProcess` run through the host's commands. Host tools that act on this machine (`ssh-keygen` for the worker key, `du`, `lsof`, `git` on coding folders) stay local and are not stack commands. dockerode users (`dockerService`, `HostResourceAttribution`, `addonHostFacts`) stay on the local engine behind `engineControl`.

Stack scripts run through `StackCommands.runScript`, which runs `bash <script>` from the stack folder; the local host's runner is `stackHost/localScript.ts`. `addon.sh`, `crm.sh`, `sync-profiles.sh` and the setup script moved. Setup takes `stackCommandsAt(root)`, since it runs before the folder is the active stack. `stackScripts.ts`' `composeOnStack` and `cliOnStack` run through `StackCommands.scriptCompose` and `scriptCli`, which run compose and the container CLI from the stack folder with the script environment. The direct `runCli`, `runCompose` and `runComposeStreaming` calls in `AssistantStackService` are the local host's own compose context, provisioning or engine control, and go behind `provision` and `engineControl` in phase 2. Tools on this machine stay local: `ssh-keygen` (`hermesWorkerKey`), `unzip` (`provisionSovereignStack`), the node and python3 probes and docker shim in `runSovereignSetup`, `git` and `du` on coding folders, the Mac calendar helper, Chrome, `launchctl`, `sysctl`, `id -F` in `addonInstaller`, `ps` in `HostResourceAttribution`, and image removal in `HostCapabilityService` and `addonRemoval`.

**1e. The guard.** `eslint.config.js` flags imports of `fs`, `fs/promises` and `child_process` (with or without `node:`) and `127.0.0.1` in string and template literals in `src/main/services/{assistant,addons,hostBridge}` (Hermes and coding code live under `assistant/`), outside tests and the vendored Hermes sources. `stackHost/` sits outside those folders. `stackGuardAllowed` lists the files that still act on this machine, each with its reason from 1c and 1d: provisioning and location resolution, the local host's own compose context in `AssistantStackService`, tools on this machine, engine port probes, host folders, operations `StackFiles` lacks, paths `.env` may set anywhere, loopback checks on URLs a person typed, and the host bridge's own listener and files. The allow list shrinks as phases land.

Live check: `bun run test:stack` passes unchanged after each step, and a Labs build starts the stack from cold with `BOUNDARY_EMULATE_NO_DOCKER=1`.

## Phase 2: capabilities

`hostFolders`, `hostCallbacks`, `provision` and `engineControl` on the host (ADR 0062 §4), all true on the local host. Each feature that needs one checks it and, when it is missing, says so where the feature appears. Tests run the features against `FakeStackHost` with each capability off.

Main reads them with `getStackCapabilities()` in `stackHost/capabilities.ts`, which needs no stack folder; features refuse with `stackCapabilityRefusal` or `requireStackCapability`, whose text is the capability's sentence in `src/shared/stackCapabilities.ts`. The renderer asks once over `stack-host:capabilities` (`useStackCapability`) and shows the same sentence with `StackCapabilityNote`. Tests turn a capability off by replacing `stackHost/capabilities` with `fakeCapabilitiesModule` from `fakeStackHost.ts`.

| Capability | Without it |

| `hostFolders` | Projects from folders and empty projects, project sources, coding folders, saving a reply, previews, the writing check's project files and revealing files or `SOUL.md` refuse. ## Phase 3: stack-owned config

The stack covers CR 0037 R3 with two interfaces, so the phase has two halves that land independently. In each, the file-based path stays as the fallback for older pins and is removed once the pin passes the version that ships the interface.

**3a. The project `.env`.** Add-on switches and `COMPOSE_PROFILES` change through `addon.sh enable|disable <id> --json`, which the pinned stack already has. Actual, Bitwarden, email, Vikunja, n8n, LightRAG and Twenty use it.

Twenty moved in two steps. First, the stack's `.env` became the only source of `TWENTY_LOCAL_ENABLED` and `TWENTY_MCP_ENABLED` in the managed install, as it already was in a local checkout, and Boundary's compose calls stopped passing them. At the first managed start after that update, `moveTwentyFlagsToEnv` writes the values Boundary used to pass, once per stack root, so an installed Twenty or a connected hosted workspace keeps its tools.

Then Get, Start, Turn off, Undo, a cancelled Get and removal moved to `addon.sh`, and Boundary's own flag writer was deleted. Twenty's manifest has an add-on-level `local` setting that owns `TWENTY_LOCAL_ENABLED`, as Actual's owns `ACTUAL_LOCAL_ENABLED`. Get and Start run `configure twenty` with `{"local": true}`, then `enable twenty` (Get adds `--reinit`, since a removal deletes the workspace that `state.json` records as set up). `enable` writes both flags, syncs `COMPOSE_PROFILES`, pulls and starts the four services with `up --wait`, runs `crm.sh init` as the init hook and reloads Hermes. Turning the local instance off runs `configure twenty` with `{"local": false}`, then `enable twenty` while a hosted workspace is stored, so its `crm-*` tools stay, or `disable twenty` when none is. Boundary still creates `data/twenty/{db,storage}` before `enable` in the managed install, removes the containers with compose, deletes the data on removal, and keeps its installed list and its own restart step. The setting is on the stack's main after v0.3.15 and in no tag yet; at v0.3.15 `configure twenty` refuses `local`, so this part ships with the pin that includes it. Unlike the plan's other steps, it keeps no file-based fallback for older pins.

Two writes of `TWENTY_MCP_ENABLED` and the installed list stay outside `addon.sh`. A hosted workspace written or removed without `crm.sh`, or removed with it, sets the flag from what is left (`syncTwentyMcpFlag`), and `moveTwentyFlagsToEnv` writes both flags once. The `crm` profile still comes from Boundary's installed list through `boundaryComposeProfilesCsv`; Circles' used services, `addonRemoval`, `twentyService` and the catalog read that list, and it can be derived from `.env` once `addon.sh list --json` reports Twenty's local instance the way it reports Actual's.

Other project `.env` keys change through the stack's `env.sh set|unset KEY --json` (`projectEnv.ts`): `HERMES_TERMINAL_BACKEND`, the image pins, the coding variables, `CONTEXT_EXTRA_ROOTS` and a managed install's `LLM_*` keys. Each change is one run under the config lock, with `STACK_CLIENT=boundary`, and a key already set to the same text isn't sent. A stack without `scripts/env.sh`, such as an older developer checkout, gets the change written to `.env` through `StackFiles`. Four kinds of write stay on the file: `LIGHTRAG_LLM_*`, which `env.sh` doesn't accept yet (CR 0037 R6); `DETECTOR_PORT`, which only a managed install with remapped ports writes, and a remote stack runs on the default ports; the keys an older Boundary wrote and now removes; and a developer checkout's `LLM_*` keys, which carry the real key and stay off the script's command line.

**3b. Profiles, profile `.env` values and `mcp_servers` entries.** These go through the client gateway's control-plane methods (`profiles.*`, `profiles.secrets.set`, `mcp.app_servers.*`), which Boundary gets by moving to the gateway as a whole, under the gateway's own CR. Those methods apply the cron fence and the bootstraps' effects, so Boundary stops running bootstrap containers after these changes. Until then a remote host writes these files over SFTP through `StackFiles`, as the local host does.

## Phase 4: remote host over SSH

`SshStackHost` keeps one SSH connection, runs commands over it, uses SFTP for files, and forwards each published port to a free local port. On connect it runs the stack's status command (CR 0037 R2) and checks the version against the pin. The host key is pinned on first connect and shown to the user to confirm; the private key stays in the OS keychain.

**The remote stack runs without Boundary's overlay.** A managed install gets most of its configuration from environment Boundary passes on every compose call (ports, `COMPOSE_PROFILES`, `HERMES_TERMINAL_BACKEND`, container and image prefixes, the `*_MCP_ENABLED` flags, coding roots, `WEB_SEARCH_URL`) and from `docker-compose.boundary.yml`. On a remote host the stack's install, upgrade hooks, `addon.sh` and status command run on the host and read only its `.env`, so a stack configured per call would drift from what they recreate. A remote stack is treated the way a developer's own checkout is: the stack's default project name and ports, with the host's `.env` as the only source of its configuration, changed through 3a. `SshStackHost` passes no compose environment of its own. What the overlay sets that a remote host still needs (the llm-proxy waiting for Boundary's push, `caldav-mcp`'s zone, the `*_MCP_ENABLED` flags) goes into `.env` through `env.sh` or setup flags; CR 0037's Background response lists the keys. The overlay's folder binds need `hostFolders`, which a remote host lacks.

**Install and upgrade.** Boundary downloads the release tarball (`sovereign-agent-stack-<version>.tar.gz`, a GitHub release asset) on this machine and refuses it unless its SHA-256 matches `SOVEREIGN_AGENT_STACK_RELEASE_SHA256`, which `check:stack-archive` checks against GitHub with the source zip's. It reads `scripts/install.sh` out of the checked tarball, uploads both over SFTP into a run folder that `mktemp -d` makes on the host, and runs `install.sh --version <pin> --dir <stack> --tarball <file> --sha256 <pin> --json` there (CR 0037 R1), so the host checks the upload again and needs no outbound access to GitHub. Setup flags such as `--db` follow `--`.

`install.sh` runs detached from the connection: under `nohup`, with no terminal and its output, pid and exit status in files in the run folder, which Boundary reads over SFTP every two seconds. An upgrade stops the stack, backs it up and replaces its files, so a dropped connection mustn't hang it up halfway; when following the run fails, the error says the run goes on and where its output is. The run folder is removed once `install.sh` has ended. Cancelling and the four-hour time limit send TERM to `install.sh` alone, and an upgrade cut off after its backup isn't rolled back, so cancelling is for a run that has stopped making progress.

The result's `needs_user` entries are returned for the user to see after an upgrade, with the hooks' `notices`; phase 5 shows them. Before an upgrade the user can choose to leave downloaded models out of the backup the upgrade makes, which passes `--skip-volume ollama_data` (CR 0037 R5); the models can be pulled again. The backup stays on the host, since it holds the browser's sign-ins and every other secret in the stack.

Install has its own path on an `SshConnection` rather than going through `SshStackHost`. `readInstalledStack` reads the stack folder over SFTP the way `install.sh` does (a `.git` checkout, `.stack-version`, or files that aren't an install), so it works on a host whose stack is at another version, stopped, or missing, and needs neither the engine nor `status.sh`. A caller reads it first, installs or upgrades when it isn't the pin, then creates the host, which keeps the guarantee that an `SshStackHost` is always at the pinned version. `status.sh` needs the engine and the Hermes image to print anything (CR 0037 R7), so connecting can't start from it.

**Endpoints.** Each TCP port in the status command's `services[].ports` is forwarded to a free port on this machine's loopback, over the same SSH connection, and becomes the endpoint for that service. A stored port key names a service and its container port (Hermes's gateway is `hermes` port 8642, the detector is `detector` port 8001), since the container side is fixed in the stack's compose file while the host side is whatever the host's `.env` sets. `portUrl` takes a port on the host, such as an add-on's port from the host's `.env`. A port whose service isn't in the stack's enabled profiles has no forward, and asking for it throws; `refreshEndpoints` reads the status again after a profile changes and forwards the new ports. A stack whose status reports another version than the pin is refused, and the error carries the version found for the upgrade step. Connecting also opens one forwarded connection to the first published port and closes it: a host whose sshd refuses forwarding (`AllowTcpForwarding no`, or `no-port-forwarding` on the key) fails then with `forwarding_refused`, rather than on the first request through an endpoint. Nothing listening on that port is fine. The terminal backend is the remote host's own `hermes-worker`, whose key the stack's setup makes.

**Secrets.** Boundary reads the dashboard password, handoff secret, `API_SERVER_KEY` and `LLM_PROXY_ADMIN_TOKEN` through the stack's credentials read, not by parsing `.env` over SFTP. The read is `scripts/credentials.sh --json`, which the stack added after v0.3.15 (CR 0037 Background); a remote host needs a pin that includes it. It runs on each call, so a secret the stack's setup rotates is read fresh.

**The stored location.** `stackHostLocation` in the `assistant-stack` store holds `StackHostLocation` (`src/shared/types/stackHostLocation.ts`): absent or `{ kind: 'local' }` for this computer, or `{ kind: 'ssh', host, port?, user, key, stackFolder, hostKeyFingerprint? }`. `key` is `{ kind: 'agent' }` (`SSH_AUTH_SOCK`, or the OpenSSH agent pipe on Windows) or `{ kind: 'file', path }` for an unencrypted key on this machine; Boundary stores the reference, not the key. A key Boundary makes and keeps in the OS keychain, and a passphrase, come with phase 5. Without `hostKeyFingerprint` Boundary doesn't connect: the selection reports the fingerprint the host offered for phase 5 to show and store. BOUNDARY_ASSISTANT_ROOT wins over a stored location, as it wins over the stored root override. A stored value that doesn't parse counts as remote and is reported, so a broken location never starts the stack on this computer.

**Selection.** Capabilities come from the stored location, not an open host: an SSH location has none of the four, connected or not, so the phase 2 checks and `StackCapabilityNote` hide or refuse the features before anything connects. `ensureAssistantStackRunning` calls `selectStackHost` when the location is remote. It connects, reads the stack folder with `readInstalledStack`, and reports a missing stack as needing an install, a release at another version as needing an upgrade, and other files as not a stack, closing the connection each time; it never installs. A git checkout's version is left to `status.sh`, which `createSshStackHost` checks. Once the host is open, the start flow waits up to a minute for Hermes's health through the forwarded port and reports ready; Boundary doesn't start a remote stack that isn't running. The host is kept until its connection closes or the location changes. `getStackHost`, `getStackFiles`, `getStackEndpoints` and `getProjectEnv` go to it, and throw `StackHostNotConnected` before it is open rather than falling back to this computer.

**Folders.** An SSH host's `localPaths` throws `not_local` when read: the stack has no folder on this computer. `getAssistantStackAccess` no longer returns `root` and `dataRoot`; the four callers that read them use `getLocalStackPaths()`, which reads `localPaths`, except Open Actual, which moved to `getStackFiles()`. With a remote location `resolveAssistantRoot` and `resolveActiveAssistantRoot` throw and `tryResolveAssistantRoot` returns no root, so code still on folders here fails or skips by name instead of using the managed install's folder. Left to move to `files`, as of 4d:

- Add-on state and installers that find the stack with `tryResolveAssistantRoot` and read it with `stackFilesAt(root)`: `addonComposeState`, `pendingRestart`, the add-on IPC handlers' listing and id check, `twentyService`, `bitwardenRuntime`, `bitwardenInstaller`, `emailInstaller`, `vikunjaInstaller`, and the `paths().root` readers in `emailAddon`, `builtinAddons` and `vikunjaAddon`. They skip or refuse on a remote stack.
- Folders on this machine by design: `stackPaths()` (`bitwardenFolders`, `stackTokenSourcesRuntime`), and Twenty's sign-in and owner password copy (`twentySignIn`, which resolves `TWENTY_PASSWORD_FILE` against the folder). They fail with `not_local`.
- Circles' shared services (`circlesService`, `usedServicesRuntime`) read Twenty's port through `stackFilesAt(root)`; they also need `hostCallbacks`.
- `AssistantStackService`'s own local paths: status building, web search mode, the overlay and coding mounts, `dropAgentMcpEnv` and the start flow after attach (`ensureAssistantStackAndApplyLlm`). The overlay and mounts sit behind `hostFolders`; applying the model on a remote stack is untested.
- `hermesProjects`, `hermesProjectSources`, `htmlPreviewFiles` and `writingVoicePaths` call `resolveActiveAssistantRoot`, behind `hostFolders` except writing voices' paths.
- `HostResourceAttribution` and the host bridge's IPC read the root for engine and bridge work behind `engineControl` and `hostCallbacks`.

The phase lands in four steps:

| Step | What | Status |
| --- | --- | --- |
| 4a | `stackHost/sshConnection.ts`, `sshStackFiles.ts`, `sshStackCommands.ts`: one `ssh2` connection with the host key checked by its SHA-256 fingerprint, `StackFiles` over SFTP and `StackCommands` over exec. Nothing uses them yet | Done |
| 4b | `stackHost/sshStackHost.ts`, `sshPortForwards.ts`: `SshStackHost`, with the status command on connect (CR 0037 R2) and the version check against the pin, a local forward for each published port as its endpoints, and the credentials read (`credentials.sh --json`). Nothing calls them yet | Done |

The SSH client is Node's `ssh2`, already in the app through `docker-modem`, with its optional native parts left unbuilt (`forge.config.ts`). It works the same on all three platforms and carries commands, SFTP and forwards on one connection; OpenSSH on Windows has no connection multiplexing, so the system `ssh` would open a connection per file read or script run. `ssh2` doesn't read `~/.ssh/config`; the host, user and key come from the stack location in Settings (phase 5), and it can use an SSH agent instead of a stored key.

On the host, commands run through the user's login shell as `cd <stack> && exec env K=V … <argv>`, with every word quoted for a POSIX shell. A variable's value is on the host's command line, where other users of that host can see it, so credentials go on stdin as they already do for `addon.sh`. Variables a caller built on top of this machine's own environment are left out, since that environment means nothing on the host. Compose runs as `docker compose` from the stack folder with no environment of its own; `scriptEnv` adds only `COMPOSE_PROFILES`, from the host's `.env`, when a caller names extra profiles. A script past its time limit or cancelled gets TERM and its channel closed. Files are written to a temp file next to the target and moved over it with `posix-rename@openssh.com`, keeping an existing file's mode; removing a folder doesn't follow links.

`bun run test:sshd` runs the SSH pieces against a throwaway OpenSSH server on 127.0.0.1, started as this user with its own keys and config in a temp folder: host key pinning, SFTP reads, writes, modes, links and removal, a script's arguments, variables, stdin and time limit, `env.sh` changing `.env` over SSH, the SSH host reading stand-in `status.sh` and `credentials.sh` and forwarding a published port, a second sshd with `AllowTcpForwarding no` refused on connect, an install through a stand-in `install.sh` that takes the real one's arguments and lines and rejects a wrong checksum, and a stored location opened only at a confirmed host key and the pinned version.

Still open: which call sites need batching before network latency matters (`projectSourcesModel`, `webSearchModeOverrides`); picking up a run that went on after the connection dropped (its run folder is named in the error, but nothing reconnects to it); `status.sh` failing with the engine down (CR 0037 R7), which makes a stopped remote stack fail to open with `script_failed`; reconnecting after the connection drops, which today waits for the next start; and the callers still on folders listed under **Folders**.

Live check: a `test:stack` variant against a Linux VM reached over SSH, and a Windows VM without nested virtualization connecting to it.

## Phase 5: choosing the location

Settings gets a stack location: this computer, or another computer with a host name, user and key. First run offers the remote host when the local engine can't start because virtualization is missing, which on Windows means WSL2 can't start a distribution. How to tell that apart from other WSL2 failures is part of the phase. Switching location doesn't move data; the page says so.

## Phase 6: callbacks and more clients

Reverse port forwards let containers on the remote host reach this machine's host bridge, inference router, Circles listeners and any model server on this machine (LM Studio, Ollama), which turns `hostCallbacks` on for remote hosts. Before this phase a remote stack reaches only upstreams it can reach itself: cloud providers, confidential pools, or a model server on the remote host. Boundary still pushes upstreams through the llm-proxy admin API over a forwarded port, and the inference settings say a model on this machine needs `hostCallbacks`. The forward has to be reachable from the remote host's container network, not only its loopback; how depends on the remote engine and is part of the phase. More than one client per stack waits for CR 0037 R4.
