# 0049. Shared folders: a folder replicated to every member of a Circle

- Date: 2026-11-09
- Status: Proposed
- Parent: [0032](0032-circles.md)
- Related: [0013](0013-project-sources-inspector.md) (folders as project sources), [0024](0024-chats-belong-to-projects.md) (a shared folder becomes a project), [0028](0028-coding-folders.md) (coding access, refused folders, hidden `.env` files), [0038](0038-changing-circle-operations.md), [0042](0042-circle-chats.md) (kept records), [0048](0048-sharing-a-service-with-a-circle.md) (sharing from one member's Mac)

## Context

Members of a Circle want to work from the same documents: notes, plans, drafts and reference material that each member's agent can read and write. Today each member keeps their own copy, synced outside Boundary with git, Obsidian Sync or the operating system's file sharing, and adds that copy to a project. That works, but Boundary knows nothing about the sync. It can't say who changed a file, can't stop a removed member from receiving updates, and leaves conflicts to whatever tool is underneath. Every member also has to set up the sync themselves.

There are two ways Boundary could own the folder.

- **Hosted.** One member's Mac keeps the folder, and other members' agents reach it through a gateway like [0048](0048-sharing-a-service-with-a-circle.md)'s, as file tools over a Protomux channel. Access can be granted and revoked per member, and writes are ordered as they arrive. The folder works only while the host's Mac is awake. Members' agents get MCP file tools instead of a mounted folder, so the coding agent, which needs a real filesystem (0028), can't work there.
- **Replicated.** The folder is a log that every member who opts in replicates, as the Circle itself is (0032 §6). Each member's Boundary writes the files into a real folder on their Mac, so agents, the coding agent and the member's own editors use it like any other folder, and it works while any member who holds the data is online. Removal is forward-only, as it already is for the Circle.

Circles already run Corestore and Autobase in the network process, and `CircleNetwork` replicates the whole Corestore over each connection to a member's device (`store.replicate`), so a new Autobase in its own namespace replicates over the connections the Circle already has.

Hyperdrive, Holepunch's filesystem module, stores a file index in a Hyperbee and file contents in Hyperblobs, but it has one writer. Several members' drives merged by the reader would have no agreed order, so two people editing the same file would see different winners. Autobase gives the order: each writer appends operations, and every peer applies them to the same view.

## Decision

1. **Boundary builds the replicated folder, not the hosted one.** It covers the common case, a group that trusts each other with the files, and keeps every member's tools working. A hosted folder stays a possible later service kind under 0048, for a folder that must not be copied to members' Macs, one too large to replicate, or one whose read access has to be revocable. Nothing in this ADR depends on it.
2. **A shared folder is its own Autobase.** Each shared folder has an Autobase in its own Corestore namespace, encrypted with its own key, and replicated over the Circle's existing connections. It is not part of the Circle's log: file operations would bloat every member's Circle log whether or not they use the folder, members choose which folders to replicate, and the folder's operations can change without moving the Circle's format.
3. **The offer is a kept Circle record.** The member who shares a folder writes a `member`-scope record (app `folders`, one key per folder) with `keep: true`, so the folder outlives its creator leaving (0042 §2). It holds the folder's name, its Autobase key and its encryption key. Every member can read the Circle's records, so every member of the Circle can read every folder shared in it. That matches the Circle itself, whose key every member holds. Folders for some members only would need the key sent by peer signal, and are later work.
4. **Each device writes contents to its own blob core.** A writer device stores file contents in a Hypercore of its own in the folder's namespace, using `hyperblobs` and encrypted with the folder's key, and appends small operations to its Autobase input. The view is a Hyperbee keyed by path, holding for each file the blob core, blob position, size, a BLAKE2b hash, a version number, and the identity and device that wrote it. `hyperblobs`, `autobase` and `hyperbee` are pinned exactly (0038 §7).
5. **Three roles.** The creator is the folder's first *manager*. Managers are the folder's Autobase indexers and add or remove editors and managers. *Editors* are writers. Every other member of the Circle who adds the folder is a *reader*. The creator picks a default role, editor or reader, for every member. A manager's device adds members who join the Circle later at that role when it next sees them, so a new member can read at once but edits only after a manager has been online. Writes are confirmed by a majority of managers (0032 §7): one of one, both of two, two of three. A second manager keeps the folder manageable if the creator leaves but makes every change wait for both, so the share sheet doesn't suggest one; it shows how many managers must be online as the creator adds them.
6. **Operations and what `apply` checks.** The operations are `put`, `del`, `add-writer`, `remove-writer`, `set-role` and `set-format`. `apply` checks that the author is a writer, and for `add-writer`, `remove-writer` and `set-role` that the author is a manager. A path is relative, uses `/`, has no `.` or `..` segments, no NUL, and is at most 1,024 bytes of UTF-8. Paths are compared after Unicode NFC normalization and case folding, because macOS's default filesystem treats `Notes.md` and `notes.md` as one file. A `put` names its blob, size and hash, and the version it was edited from (`base`). The folder's Autobase has its own format from its first build, and 0038's rules apply to it.
7. **Conflicts become copies, decided in `apply`.** A `put` whose `base` is the current version replaces the file. A `put` whose `base` is older, because someone else's edit was ordered first, is stored beside it as `<name> (conflict, <member>).<ext>`, and the original keeps the earlier edit. An edit ordered after a delete restores the file. Because `apply` decides from the order alone, every peer ends with the same files once the order is confirmed. Merging text is later work.
8. **Each member mirrors the folder into a real folder on their Mac.** **Add to this Mac** asks for a location, by default `~/Circles/<Circle>/<folder>`, and refuses the folders 0028 §5 refuses. It warns when the location is inside another sync tool's folder (iCloud Drive, Dropbox, Google Drive, OneDrive), because two sync engines on one folder overwrite each other.
   - Remote changes are written to a temporary file inside the folder and renamed into place, so no program sees a half-written file.
   - A file watcher turns local changes into operations once a file has stopped changing for two seconds. A change whose hash matches what Boundary last wrote is not sent, so Boundary's own writes don't loop back.
   - Readers' copies are written read-only. A local edit by a reader is never sent; if a remote update arrives, the edit is kept as a conflict copy that only that reader has.
9. **Some files are never shared.** `.git/`, `node_modules/`, `.DS_Store`, symbolic links, and `.env` and `.env.*` files (but not `.env.example`, `.env.sample` or `.env.template`, as in 0028 §6) stay on the Mac they were written on. So do files over 100 MB. The folder's status lists each unshared file with the reason. Sharing an existing folder that is a git repository is refused, and the sheet points to git for code.
10. **A shared folder becomes a project on each Mac.** **Add to this Mac** makes a new project whose own folder is the mirror, named after the shared folder, so chats about it start in the right place (0024). The member can instead add the mirror to an existing project as an extra folder. Either way the project stays the member's own: its chats, instructions and model choice are not shared. Coding access starts off, as for other new projects (0028 §12), and only an editor can turn it on. Agents use the mirror as an ordinary folder: as a read-only source (0013) for any member, or with coding access (0028) for an editor. Hermes and the coding agent use their own file tools, with no MCP server and no gateway. The project's Folders list marks the folder **Shared with <Circle>**, and adding it states that whatever an agent writes there goes to every member of the Circle. Boundary attributes changes to the member and device that made them. It can't tell a member's own edit from their agent's, because both reach the folder as file writes.
11. **History comes from the logs, fetched when asked for.** Every version stays in its author's blob core, so each file has a history and **Restore** writes an old version as a new `put`. Replication is sparse: a member's Mac downloads the blobs of each file's current version, and older versions only when someone opens the history. A writer's Mac always holds its own blobs. Because replication is sparse, a change's contents reach other members only once an online device has fetched them: a peer passes on only blocks it holds. Each member's Boundary therefore downloads current versions as soon as the view shows them, and a change is only on its author's Mac until another member's Mac has downloaded it.
12. **Removal is forward-only, and Boundary never deletes a member's files.** When a member leaves or is removed from the Circle, a manager's device appends `remove-writer` for their devices in each of the Circle's folders when it next sees the removal, because a folder's `apply` can't read the Circle's view. The removed device stops syncing when it gets the removal notice (0032 §6) and forgets the folder keys with the Circle's. The mirrored files stay on that Mac, marked as no longer shared. A member who turns off **Add to this Mac** stops replicating and chooses whether to keep the files or move them to the Trash.
13. **Shared folders live with their Circle in the chat.** A Circle's place in the chat (0042 §10, 0043) lists its shared folders with each one's sync state: up to date, syncing, unconfirmed changes, files not shared, or a conflict. **Share a folder…** creates an empty folder or shares an existing one, and shows the total size every member who adds it will download.
14. **Logs carry metadata only.** The network process and main log folder ids, operation counts, sizes, timings and errors, never paths or file contents, because file names can say as much as the files.

## Consequences

- Every member who adds a folder downloads every file in it and keeps what they downloaded after leaving. The share sheet and the remove dialog say so, as the Circle's do.
- Edits confirm only when a majority of the folder's managers is online. Until then other members see them with an unconfirmed mark, and a reorder can turn an unconfirmed edit into a conflict copy. A folder whose managers have all left can still be read and edited, but nothing new confirms and no editors can be added.
- A shared folder syncs whole files, so it can't hold a database an app keeps open, such as a SQLite file with its `-wal`: two Macs writing their own copies would produce conflict copies or a corrupt file. Sharing an app's data between members needs that app's own sync and is outside this ADR.
- Two members editing the same file at the same time get a conflict copy, not a merge. For documents that people edit together all day, that is worse than a shared editor, and text merging is the first thing to add if it happens often.
- A member's agent reads files other members wrote. Those files are untrusted text in the same way a web page is, and a member who marks nobody **Trusted** (0034 §3) gets no extra protection here, because the folder is an ordinary folder to Hermes.
- Each member's disk use grows with the folder's current size; history costs disk only on the writer's Mac and for versions someone opened. Autobase can't prune the operation logs.
- Adding `hyperblobs` adds a module to the network process's packaging, which phase 0 of the circles plan proved for the others.
- Shared folders need nothing from the agent stack. They reach Hermes and the coding agent through the existing project folder and coding grant paths, so `docs/stack-contract.md` gains no rows.
- [What the pinned modules do](../shared-folders-modules.md) answers the module questions: blobs replicate sparsely and can be cleared, a removed editor's offline writes aren't applied, and `fs.watch` reports paths but not what happened to them, so the mirror stats and hashes each path and rescans on open.
- The flows are designed in the [shared folders study](../shared-folders-ux-study/spec.md), with a click-through.
