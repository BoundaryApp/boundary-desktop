# 0048. Sharing a service with a Circle

- Date: 2026-11-08
- Status: Proposed
- Parent: [0032](0032-circles.md)
- Related: [0034](0034-shared-models.md) (the gateway this follows), [0027](0027-host-bridge.md) (loopback listeners reached from containers), [0038](0038-changing-circle-operations.md), [0039](0039-shared-models-that-cant-serve.md), [add-ons spec](../addons-ux-study/spec.md), [change request 0020](../change-requests/0020-ui-installable-addons.md), [change request 0023](../change-requests/0023-twenty-workspaces-access-sign-in.md)

## Context

A member who runs Twenty on their Mac wants the rest of their Circle's agents to look up and change records in it, so the Circle works from one CRM. Shared models ([0034](0034-shared-models.md)) already let one member run a service for their Circle: an offer in the Circle's log, a Protomux channel that accepts only current members' devices, a narrow set of endpoints forwarded to a local server, counts per member, and settings the consumer sets for each provider. A CRM differs from a model in three ways.

- **It keeps what members write.** Every record a member's agent creates lives on the provider's Mac. The provider can read members' queries and the records they write, and the records outlast the request.
- **Access is per person.** Some members should only look things up. A single key shared by everyone would let any member write, would make every change look like the same author in Twenty, and couldn't be taken back from one member without breaking the others.
- **Agents reach it as tools, not as a model.** Hermes calls Twenty through its `/mcp` endpoint, registered as `mcp_servers.crm-<slug>` from a workspace file in `compose/twenty/workspaces/`. Tool results feed the consumer's agent the same way a shared model's replies do.

The stack already registers workspaces Boundary didn't create. Checked in `../assistant` at the pinned tag: `crm.sh add --slug S --url URL` accepts any `http://` or `https://` URL, strips a trailing `/mcp`, sends an MCP `initialize` to `<url>/mcp` with each key in the environment, and writes the file only after a 200. `bootstrap-api-profile.sh` registers each `*.env` there as `crm-<slug>`. The `hermes` service has `host.docker.internal:host-gateway`, and [0027](0027-host-bridge.md) §1 relies on containers reaching a host listener bound to `127.0.0.1` through that name.

Sharing belongs to one instance, a workspace, not to an add-on: a member can run a local Twenty and connect a hosted one, and share either, both or neither. Whether an add-on can be shared at all, and how, is a property of the add-on.

## Decision

1. **A shared service is an offer, a gateway and a tunnel.** The provider publishes an offer, a `service` channel on the provider's Mac forwards members' requests to the instance, and the consumer's Mac exposes the channel as a local listener the stack registers like any other workspace. Twenty is the first kind. Shared models keep their own `inference` channel and offer shape, so peers on older builds see no change; the two gateways share the membership check, the queue and the counts in code.
2. **The offer is a Circle record.** Each provider writes one `member`-scope record (app `services`, one key per offered service) with the kind, a display name, the access levels offered (`read`, or `read` and `write`) and an away flag. No new Autobase operation is needed, so 0038 doesn't apply. Grants for individual members and every key stay on the provider's Mac, never in the log, because every member can read the log and keeps it after leaving. Whether the provider is reachable comes from live connections, as for models.
3. **The gateway forwards only the service's tool endpoint.** For Twenty that is `POST /mcp` to the instance's own URL, with the request's `Accept` header kept so Twenty answers with JSON or an event stream as the client asked. Twenty's MCP controller has no `GET` or `DELETE` route and keeps no MCP session, so nothing else is needed. Twenty's REST and GraphQL APIs, its web app and its admin routes are never reachable. Requests come only from devices of current members of the Circle the offer is in, and only for a member the provider has granted access to.
4. **Each member gets their own keys, held by the provider.** When the provider grants a member access, the provider's Boundary creates an API key in Twenty for that member with the role for each level granted (the read-only and read-write roles `crm init` makes), named after the member and Circle. The gateway swaps the consumer's placeholder for that member's key as it forwards a request. Twenty records a change made with a key as `createdBy` with source `API` and the key's name, so each member's changes carry their name, and removing one member revokes only their keys. Keys never leave the provider's Mac.
5. **The consumer reaches it through a loopback listener the stack registers.** The consumer's Boundary opens a listener on `127.0.0.1`, hardened as [0027](0027-host-bridge.md) §2 requires, with a port chosen once per shared service and kept across launches. It registers it as a workspace in the Twenty add-on's store, with the URL `http://host.docker.internal:<port>` and, as `key_ro` and `key_rw`, random tokens that the listener checks and that unlock only the levels the provider granted. Boundary writes the store's files itself, in the layout `crm.sh` writes, because `crm.sh` checks the URL from the Mac, where `host.docker.internal` doesn't resolve. `TWENTY_ACCESS` picks between them as it does for any workspace, and unattended runs get the read token. The slug is derived from the provider's and Circle's names and is unique on the Mac. If the kept port is taken at launch, Boundary picks another, rewrites the file, and adds the change to the restart bar (add-ons decision 16).
6. **Using a shared service is the consumer's choice.** An offer shows in the consumer's list but registers nothing until they turn on **Use in my agent**. Each registered server adds tool definitions to every turn and needs the assistant to reload, so offers don't register themselves.
7. **Trust follows 0034 §3, with the meaning changed for a service.** Both settings attach to the provider's identity and are shared with their models.
   - **Private** reads, for a service, as "I accept that this person holds what my agent sends and writes there." A shared service serves privacy-locked projects only when its provider is marked private.
   - **Trusted** reads, as for models, as "I accept that this person's results can drive my agent." Without it, Boundary registers the server with `trust: untrusted`, so Hermes asks before every call whose tool lacks `readOnlyHint=true`. For Twenty that is every call, because every record call goes through `execute_tool`. Change request 0023 R3 would make this ask before writes only.
8. **The provider's settings.** On the instance's row, **Share with a Circle…** picks the Circle, the default access for members, overrides per member, and away mode, which holds a power-save blocker while Boundary is open as 0034 §4 does. A shared row shows who has used it today, with request counts per member, and **Stop sharing**. Counts stay on the provider's Mac and the consumer's, as in 0034 §5. This ADR adds no quotas.
9. **Removal and stopping revoke keys.** When a member leaves or is removed, or the provider stops sharing or narrows a grant, the provider's Boundary deletes that member's keys in Twenty. If the provider's Mac is off at the time, it does this when it next opens the Circle; meanwhile the gateway already refuses the member, because they are no longer in the Circle's view.
10. **A hosted instance is shared by handing out keys, with no gateway.** When the shared workspace is hosted, the provider's Boundary creates the member's keys the same way, and sends them to that one identity in a peer signal, never in the log. The member's Boundary connects the workspace directly with `crm.sh add`. The service then works while the provider is offline. Revocation (decision 9) is the only way to take access back, and it runs from the provider's Boundary.
11. **Offline is said, not guessed.** When the provider can't be reached, the consumer's listener answers with an error naming the person and that their Mac is offline. A tool call in the chat shows that text, and the provenance line names the person and Circle the service is shared from.
12. **Add-ons declare whether they can be shared.** The add-on manifest gains a `share` object: the paths and methods the gateway may forward, how to create and delete a key for a member at each level, and which levels exist. Until `addon.sh` ships the manifest (0020 R1), Boundary's compiled catalog carries it for Twenty. Local models are already shared through 0034. Signal, Mail and Messages are never shareable, because they act as the user.
13. **Logs carry metadata only.** The gateway and the listener log member identity, service, the JSON-RPC method and tool name, status and timings. Arguments and results are never logged, as in 0034 §6.

## Consequences

- A CRM shared from a Mac works only while that Mac is awake and Boundary is open. A Circle that relies on its CRM should share a hosted workspace (decision 10). The share sheet says which kind the workspace is and what that means.
- Members use a shared local Twenty through their agents only. Opening Twenty's web app over the tunnel needs a Twenty user per member and the whole app proxied on another origin, which this ADR doesn't cover.
- **Use in my agent** works with the provider offline, because nothing checks the workspace before it is written. The first tool call says so if they still are (decision 11).
- Creating and revoking keys per member is Boundary glue against Twenty's API until the stack offers it ([change request 0025](../change-requests/0025-twenty-member-keys.md)). Checked in Twenty's source at the `twenty/v2.55.0` tag, the version the stack pins: `createApiKey` takes a name, an expiry and a `roleId` and needs a user session with the Roles permission, not an API key; `generateApiKeyToken` returns the token; `revokeApiKey` revokes one key by id; `buildCreatedByFromApiKey` sets `createdBy` to source `API` with the key's name; and `McpCoreController` has one `POST` route that answers JSON, or an event stream when `Accept` includes `text/event-stream`. The stack's `twenty_admin.py` already mints its two keys the same way, against roles it finds by label.
- A provider's gateway sees every query and write members send it. Like a shared model, the settings in decision 7 are claims the user makes about a person, and the UI states them as such.
- `docs/stack-contract.md` has rows for the workspace files Boundary writes, the stack's registration plan for them, the `hermes` service's `host-gateway` entry, and how Hermes's MCP client shows an error.
