# 0050. GIFs in Circle chats: the bytes travel through the Circle, not from a GIF service

- Date: 2026-11-09
- Status: Proposed
- Parent: [0042](0042-circle-chats.md)
- Amends: [0042](0042-circle-chats.md) §3 (a `media` field on `chat-post` at format 3), [Circle chats spec](../circle-chats-ux-study/spec.md) decision 11 and acceptance criterion 15
- Amended by: [0051](0051-circle-notifications-and-mentions.md) (§9: format 3 also carries `mentions`, and **Turn on GIFs** becomes **Update this Circle**)
- Related: [0038](0038-changing-circle-operations.md), [0049](0049-shared-folders.md) (per-device blob cores), [shared folders modules](../shared-folders-modules.md)

## Context

People want to post GIFs in Circle chats. Today they can't, on purpose. The Circle chats spec's decision 11 allows Markdown "minus images and raw HTML, so a message never loads anything from the network", and its out-of-scope list says attachments and images "would need a blob store in the Circle". The thread passes `disallowedElements={['img']}` to Streamdown to enforce it. The app's Content Security Policy allows `img-src 'self' data: https:`, so that filter is the only thing keeping remote images out of the thread.

A message can't carry the image itself. `apply` caps `text` at 12 KB of UTF-8 and the whole `chat-post` at 16 KB of JSON, and a typical GIF is hundreds of kilobytes to a few megabytes. Every message is also replicated to every member for as long as the Circle exists (0042, Consequences), so large values in the log would cost every member disk whether or not they ever scroll back.

There are two ways to show a GIF.

- **Link to a GIF service.** The message stores a URL on a GIF service's CDN, and every member's app fetches it when it renders. This needs only a picker, a message field and an exception to the image filter. But every member who opens the channel sends a request to that service, which learns their IP address and roughly when they read the chat, and a URL's contents can change after it's posted. That is the network load decision 11 rules out, now made by every reader instead of one writer.
- **Carry the bytes in the Circle.** The sender's Mac gets the GIF, stores it in a blob core of its own, and posts a small reference. Other members' Macs fetch the bytes from Circle peers over the connections the Circle already has, check them against a hash, and show them. Only the sender ever contacts a GIF service, and only if they search one. Shared folders already store contents this way (0049 §4, §11): each writer device has a `hyperblobs` core in the folder's namespace, encrypted with the folder's key, and readers download blocks sparsely from any peer that holds them. `hyperblobs` is already pinned in `package.json`.

`chat-post` cuts each message to its known fields (`shared`, `agent`, `call`), so a new field means a new format under 0038 §3. No Circle has moved past format 2, and nothing in the app yet asks for `set-format`: `CircleNetwork.setFormat` exists, but no request or UI calls it.

## Decision

1. **GIFs travel through the Circle.** A GIF's bytes are stored by the sender's device and fetched from Circle peers. No member's app loads a GIF from outside the Circle when it renders a message. Decision 11 of the spec changes from "a message never loads anything from the network" to "a message never loads anything from outside its Circle".
2. **Each device keeps one media blob core per Circle.** It is a `hyperblobs` core in the Circle's Corestore namespace, encrypted with the Circle's key, written only by that device, and replicated sparsely over the Circle's existing connections, as 0049 §4 does for folders. Its key travels in each message's reference, so joining a Circle needs no new operation and no change to the member intro.
3. **Format 3 adds `media` to `chat-post`.** `media` is a list of one item for now, so a later change can allow more than one without a format 4. Each item is `{ core, blockOffset, blockLength, byteOffset, byteLength, hash, type, width, height }`: the blob's position as `hyperblobs` gives it, its BLAKE2b hash, its type and its pixel size. `apply` checks shape only: `core` and `hash` are 64 hex characters, the offsets and lengths are non-negative safe integers, `byteLength` is at most 8 MiB, `type` is `image/gif` or `image/webp`, and `width` and `height` are integers from 1 to 2,048. A post with `media` may have empty text, as a post with `call` may. `chat-edit` changes text only and never adds, removes or replaces media. At formats 2 and below, `media` is dropped as an unknown field, as today.
4. **Receivers check before they show.** When a message with `media` enters the view, the network process downloads the blob, up to `byteLength`, from any peer that holds it. It shows nothing until the bytes match `hash` and `byteLength`, start with the signature for `type` (`GIF87a`/`GIF89a`, or `RIFF`…`WEBP`), and declare the width and height in the message. A blob that fails any check shows as "This GIF couldn't be shown" and is cleared. Downloads start as soon as the view shows the message, not when it scrolls into sight, so a GIF still arrives after its sender goes offline, for the same reason as 0049 §11.
5. **The renderer gets checked bytes through an app protocol.** Main registers a privileged scheme that serves a checked blob by Circle, author and message id, and the Content Security Policy's `img-src` adds that scheme. The thread renders `media` as an image element pointing at it, outside the Markdown, so Streamdown keeps refusing `img` and Markdown images in message text stay off. Main serves only blobs that passed decision 4, and only to the app's own page.
6. **Sending.** The composer gets a GIF button and accepts a pasted or dropped `.gif` or `.webp`. Main reads the file, applies the checks in decision 4, writes it to the device's blob core, then appends the post. A file over the caps is refused before anything is written, with its size and the limit. The composer shows the GIF as part of the draft, and the existing warning that every member keeps a copy covers it.
7. **Searching a GIF service is a later phase, from the sender's Mac only.** A search picker sends the query to one provider from the sender's Mac, downloads the chosen GIF there, and then follows decision 6, so receivers never contact the provider. The picker says that the provider sees what the sender searches for. The provider, its terms, its attribution rules and how the app holds an API key are decided before that phase starts. Search queries are never logged.
8. **Deleting clears the bytes where it can.** When the author deletes a message, their device clears the blob from its own core. When anyone's device sees a deleted message, it clears its local copy. Members who downloaded the GIF before the delete had it on disk, and an admin's delete can't clear the author's core, so the UI still says a deleted message is hidden, not destroyed (0042 §5).
9. **A Circle moves to format 3 when an admin turns GIFs on.** New Circles start at format 3. In an existing Circle, the composer has no GIF button until an admin chooses **Turn on GIFs** in the Circle's details, which appends `set-format` to 3 after a sheet saying that members on builds without format 3 will see the Circle stop until they update (0038 §4, §5). This is the first request and UI for `set-format`, and other format 3 changes should ship with it, so Circles move once.
10. **Logs carry metadata only.** The network process and main log blob sizes, types, timings, check failures by kind and download sources by count. They never log message text, search queries or file names.

## Consequences

- Each member's disk grows with every GIF posted in each Circle they belong to, until the message is deleted. At 2 MB a GIF, a Circle that posts 20 a day adds about 15 GB a year to each member's disk, which is much more than text (0042, Consequences). A per-Circle setting to stop downloading media, or to download it only when it scrolls into sight, is the first thing to add if this hurts.
- A GIF reaches other members only once some online device has downloaded it. A sender who posts and quits before anyone else is online leaves a message that shows the GIF's size and "Waiting for someone who has this GIF to come online" until the sender returns.
- Members keep the GIFs they downloaded after they leave or are removed, as with messages and folder files.
- Chromium decodes images that other members chose, in the renderer process. The checks in decision 4 limit size and type but don't make a malformed image safe to decode; the renderer's sandbox does that, as it does for any image on a web page.
- The blob core and the receive checks are a general media path. Still images and other attachments can use them later, behind their own decision on types and caps, with no new format if they fit decision 3's fields.
- A sender who searches a GIF service sends their queries and IP address to it. Receivers send nothing, which is the point of this ADR.
- Raising a Circle's format stops it for members on older builds until they update. Decision 9 makes that an admin's choice per Circle rather than a side effect of an update.
- GIFs need nothing from the agent stack, so `docs/stack-contract.md` gains no rows.
