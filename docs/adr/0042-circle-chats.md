# 0042. Circle chats: kept in the Circle's log, shown in the Workbench chat as a place

- Date: 2026-11-02
- Status: Proposed
- Parent: [0032](0032-circles.md)
- Amended by: [0043](0043-circles-live-in-the-chat.md) (no Circles destination), [0044](0044-circle-calls.md) (§3: a `call` field)
- Related: [0008](0008-multi-agent-channels-and-wake.md), [0010](0010-durable-attribution-and-room-lifecycle.md), [0023](0023-chat-types-and-hermes-home.md), [0024](0024-chats-belong-to-projects.md), [0034](0034-shared-models.md), [0038](0038-changing-circle-operations.md), [Autobase 7: writers' entries while no indexer is online](../circles-autobase-confirmation.md), [circles plan](../circles-plan.md) phase 5, [Circle chats spec](../circle-chats-ux-study/spec.md)

## Context

ADR 0032 §3 and §8 put a Circle's chat channels in its Autobase and keep them apart from Hermes chats. Phase 5 of the circles plan builds them. Three things already exist that phase 5 can use: [Circle records](../circles-plan.md#circle-records) (one JSON value per key, up to 16 KB, admin-only at `circle` scope, deleted with their member at `member` scope), [peer signals](../circles-plan.md#peer-signals) (ordered, unkept, 4 KB, 30 a second), and ADR 0038's format rule. No Circle exists past format 1, and `setFormat` has no request or UI.

Records can't hold messages. Each record is read by a whole-state scan on every view update and reported in full when a Circle opens, which is fine for settings and wrong for thousands of messages. Keys are flat, so there is no cheap "the 50 before this one". And `remove-member` deletes a member's records, so a departed member's messages would vanish from everyone's chat, which is not what people expect of a group chat.

A second change already needs format 2: making `member` records outlive their member, with `record-set` taking `keep` and `record-del` taking an `identity` an admin can clear. Each format costs a two-sided release.

The Workbench chat already has most of what a group chat needs: rooms with members (0008), a who-line on every message (0010), `@` to wake someone and posts that wake no one (0009), Mentions, message actions and a composer, built on assistant-ui. People will want their agents in Circle chats too, and the Workbench chat is where agents already talk with people. A second chat interface on the Circles screen would duplicate all of it and then have to merge when agents arrive.

Putting Circle channels in the same rail as Hermes chats, agent channels and agent DMs makes every row a different kind of conversation with a different audience, and people have to work out from each row who will read what they type. The rail already has a scope: since 0024 it shows one project at a time, and **Go to project** changes what it lists. A Circle is a scope of the same kind, one level up. When someone is in a Circle, they want the chat to be that Circle, not a list in which the Circle is one section.

Confirmation timing is measured: at Boundary's 10-second ack interval an entry takes 29 to 54 seconds to confirm when an admin returns, and Autobase pushes the ack timer back on every update, so a busy chat confirms later. In a Circle with three or more admins, one online admin isn't a majority.

## Decision

1. **Messages are Autobase operations at format 2.** `chat-post`, `chat-edit` and `chat-delete` apply only once the Circle's format is 2; earlier formats skip them, as ADR 0038 §3 requires. Channels are Circle records under the `chat` app, so creating, renaming and removing a channel adds no operation.
2. **Format 2 also carries the kept-record changes.** `record-set` takes `keep: true` and `remove-member` leaves kept records in place. `record-del` takes an optional `identity`, which lets an admin delete a kept record whose owner is no longer a member, and nothing else. Circles change format once for both.
3. **What `apply` checks.** The author is a current member. `channel` matches the record-name pattern. `id` is 16 to 32 lowercase hex characters chosen by the author's device, unique per author and channel; a repeat is skipped. `text` is non-empty, except on a post with `call` ([0044](0044-circle-calls.md) §7), and at most 12 KB of UTF-8, and the whole operation at most 16 KB of JSON. `at` is the author's clock in milliseconds and is shown, never used for order, because `apply` has no clock. An optional `shared` names where shared text came from (decision 9), an optional `agent` names which of the author's agents wrote it (decision 12), and an optional `call` of `{ id, ended? }` on posts and edits marks a call's start and end (0044 §7); each is checked for shape and length. `apply` doesn't check that the channel has a record; readers ignore channels that don't.
4. **How the view holds a channel.** Each channel keeps a count, and a post is stored under its position in that channel, with an index from `author/id` to the position. The view copies the author's display name into the message, so a message keeps its name after its author leaves. A reorder recomputes positions deterministically, so they agree once confirmed; until then everything outside `apply` names a message by `author/id`, never by position.
5. **Edits and deletes.** Only the author edits, and the view keeps the latest text with an `edited` flag. The author or any admin deletes; the view drops the text and keeps a stub that says who removed it. Neither erases anything: the original operation stays in the author's core, which every member replicates, so the UI says a deleted message is hidden, not destroyed.
6. **Confirmation.** A message is confirmed when its view block is below the view's `signedLength`, as records are. Unconfirmed messages show at once, in the view's current order, with an unconfirmed mark. Nothing outside `apply` numbers messages or anchors to a position until they are confirmed. A message whose author's removal is ordered before it disappears when the order settles, and the UI reports it as gone.
7. **Leaving and removal.** `remove-member` leaves a member's messages in the chat. A removed or departing member's device closes the Circle and forgets its keys (ADR 0032 §6), which takes the chat off that Mac with the rest of the Circle. Anything they copied or a modified build kept stays with them, and the remove dialog already says so.
8. **Typing and read marks are peer signals.** `chat.typing` and `chat.read` carry a channel and, for reads, the newest message id read. They are never kept, so a member offline at the time never sees them. Each device keeps its own read position per channel in main's Circles store, outside the Autobase, so unread counts never reach the Circle.
9. **Sharing from a Hermes chat is one message, by hand.** A Hermes chat message gets **Share to Circle…**, which opens a sheet with that message's text in an editable box, a Circle and channel picker, and the warning that every member keeps a copy. Only the text in the box is posted, and only when the user presses **Share**. Tool calls, tool results, reasoning, attachments, other messages, the session id and the chat's title are never sent. `shared` records the role (`user` or `assistant`) and, for an assistant reply, the model name the chat showed.
10. **The chat rail shows one place at a time.** A place is either **This Mac** or one Circle, and a switcher at the top of the rail moves between them.
    - **This Mac** is the rail as it is today: **Go to project** and projects (0024), All chats, Mentions, Hermes chats, agent channels and agent DMs. No Circle appears in it.
    - **A Circle** shows only that Circle: its channels, its people with their presence, and the agents its members have brought (decision 12). It has no projects, Hermes chats, Mentions or agent DMs.
    - The switcher lists This Mac and every Circle, each with its unread count, and shows the count of unread messages in other places, so being in one place doesn't hide activity in another. Each place reopens the conversation that was last open in it.
    - Opening a conversation from elsewhere (a notification, a share toast, the Circles screen's **Open chat**, ⌘N for a new Hermes chat) switches to its place.
    - The place is a property of the chat screen only. Other screens, such as Tasks and Settings, don't change with it.

    A Circle channel is a conversation type in the Workbench chat. It joins the four of 0023 with the Circles mark as its shape. The thread, who-lines, day dividers, message actions, `@` menu and composer are the Workbench ones, fed from the Circle's view through an assistant-ui external store instead of a Hermes session. Actions that only mean something for Hermes (Retry, Branch, the DM horizon) don't appear; Circle-only marks (unconfirmed, **Left**, seen-by, an admin's delete) are added. The Circles screen keeps people, sharing and invites, with **Open chat** in a Circle's header, and has no Chat tab; [0043](0043-circles-live-in-the-chat.md) later moves those into the chat and retires the screen.
    Main exposes channels and messages as functions, as it does records, with a new-message event, and the renderer gets the same through IPC and a hook. The thread has a compact layout that works at 320px with messages from props, so another screen can mount a Circle channel. Every Circle has a default channel, `general`, that needs no record.
11. **Circles start at format 2, and nothing older is handled.** No format 1 Circle exists on any install, so the format 2 build has no wipe, upgrade or notice. New Circles start at format 2, and an admin's device refuses joiners whose build declares format 1 (ADR 0038 §6). `set-format` still has no request or UI.
12. **Agents join a Circle the way people do, later.** An agent is in a Circle only when its owner brings it, and then it is listed beside the people as "Maya's Hermes", marked as an agent and as Maya's. Format 2 reserves what this needs: `chat-post` takes an optional `agent` of `{ slug, name }`, a label under the posting member's identity, so the message stays Maya's for edits, deletes and removal, and a member can only ever speak as their own agents. Which agents a member has brought is a `member`-scope Circle record, so it needs no operation and leaves with its owner. This ADR builds neither bringing an agent nor letting it read or reply; it stores and shows the field so that adding them needs no format 3. When it's designed, these hold:
    - the owner's Mac runs the agent and posts its reply;
    - an agent replies only when `@`-mentioned (0008);
    - a mention from anyone but the owner waits for the owner's approval;
    - a reply woken by someone else asks before every side-effecting tool call, like an untrusted provider's turns (0034).
13. **The two kinds of chat stay visibly apart.** A Hermes chat stays on this Mac; a Circle message goes to every member and can't be taken back. They are never in the same rail (decision 10). Inside a Circle, the switcher names it, the channel's header names the Circle and its people, the composer reads "Message Book club · 4 people" and carries the Circle mark, and nothing moves text from This Mac into a Circle except the share sheet.
14. **No direct messages inside a Circle yet.** Every member's device replicates the whole Circle log and holds its key, so a two-person message stored there could be read by every member, whatever the UI showed. A private one needs either live peer signals, which arrive only while both people are online and are never kept, or a message encrypted to its recipient, which still shows the other members who wrote to whom. Until one of those is chosen in its own ADR, a person's row in a Circle opens their details, not a conversation. When DMs come, they are with people in the current Circle only.

## Consequences

- Chat history only grows. Every member replicates every message, edit and delete for as long as the Circle exists, and Autobase has no way to prune. At 1 KB a message, a Circle that sends 1,000 messages a day adds about 365 MB a year to each member's disk.
- Members on older builds can't join a Circle until they update.
- Ordering is final only after confirmation, and normal confirmation takes up to about a minute. The UI shows the unconfirmed mark often, so it has to be quiet.
- A member with a skewed clock shows wrong times on their messages. Order doesn't depend on it.
- `apply` can't rate-limit, because it has no clock. A member can flood a channel; the remedies are an admin deleting messages and removing the member.
- Kept records and messages both outlive their author, so "removal is forward-only" now covers what stays in the Circle as well as what the removed member holds.
- The Circles screen spec's decision 14 changes: there is no Chat tab, and a Circle's header gets **Open chat**, which switches the chat to that Circle.
- A place sits above a project. Projects (0024) exist only in This Mac, and a Circle has none. Opening a Hermes chat always switches to This Mac, so a Hermes chat is never shown in a Circle's rail.
- Activity in places the user isn't in reaches them only through counts on the switcher and the Chat icon until desktop notifications are decided.
- The Workbench thread now serves two sources. Its mounted tests cover both, and a change made for Hermes must not assume a Hermes session id, run state or turn.
- An agent's message in a Circle is only as trustworthy as its owner, since the `agent` label is the owner's claim.
- Sharing from a Hermes chat is the only path from Hermes into a Circle. It reads only text the renderer already shows, so it adds no dependency on the agent stack.
